## Context

Explore notes: what a PC can show without hardware, feature by feature. The building blocks exist: the local simulator runtime image (`CANOPEN_FORCE_SIMULATE=1`), simulated networks with simulated devices built from EDS files, live simulation control per network (`sim_*` with `network`), a master and the plugin's own slave on one simulated bus, and the project generator (`--new-project`). The gaps found:

1. The simulation file serves one-network configs only (`canopen-simulated-bus`, "Simulation with several networks").
2. A gateway's upper network needs a master; in the container only a master network of the same config can be that master.
3. Bus error states, bit rate detection, slcan, PC-direct adapters and program download cannot be shown virtually today.

## Goals / Non-Goals

**Goals:** one project that shows every feature a PC can show; a guide a newcomer can follow on Windows, macOS or Linux with only the container engine, the PC tools and the editor; CI that runs the example so it never rots.

**Non-Goals:** closing gap 3 (each is a feature of its own); a second example per feature; screenshots of the editor in CI.

## Decisions

### One project, four networks
`io`, `motion`, `cell`, `host` on simulated buses `sim0`, `sim1`, `sim2` (`cell` and `host` share `sim2`, the one master plus one slave a simulated bus allows). Interface names starting with `sim` make it obvious no hardware is meant. `adapter.simulate: true` is set explicitly rather than relying on the image's forced simulation, so the project also runs simulated on a Pi, and so the deploy tool's check accepts `cell` and `host` on one interface (it only allows that for simulated networks).

Alternative: a tour over the existing `config/` examples. Rejected as the main shape because it never shows the features working together (gateway routes from a real-looking I/O network, one program using all of them), but the guide links each chapter to the small example too.

### The upper master is a network of the same config
`host` is a master network on `sim2` with node 20 `"simulate": false` (the plugin's own slave answers as node 20). It configures the slave's PDOs, sends SYNC and supervises it, and the demo program uses its PDO entries to play the machine controller (setpoint down, status up). Order in the file: `io`, `motion`, `cell`, `host`, so the gateway status publishes `io` and `motion` first. The guide says plainly that `host` is a stand-in.

### Simulation file version 2
```json
{ "schema_version": 2, "tick_ms": 10,
  "networks": {
    "io":     { "nodes": { "5": { "sources": { "0x7130:1": { "sine": { "min": 200, "max": 260, "period_s": 30 } } } } },
                "extra_devices": [ { "name": "new_io", "eds": "dio16.eds" } ],
                "scenarios": [ ... ] },
    "motion": { "nodes": { "4": { "drive": { "max_velocity": 50000 } } } } } }
```
Each section has the version 1 keys except `tick_ms`, which stays top level (one simulator tick per plugin). A section is matched to a network by name; a section for a network that is not in the config is an error, a network without a section gets default behaviour. Expressions and scenario conditions refer to nodes of their own network only (`[5/0x7130:1]`); a cross-network formula is not needed by the example and would need new syntax. Version 1 stays valid for a one-network config; a version 1 file with a several-network config keeps today's warning and is not used. The configurator's Simulation file editor works on the section of the network chosen in its network picker and writes version 2 whenever the config has several networks.

Alternative: one simulation file per network (`simulation.<name>.json`). Rejected: more files to carry through the editor upload and the deploy bundle, which today carry exactly one.

### DIO-16, a made-up CiA 401 module
Generated by a `make_eds.py` like RTD-8 and SD-402: 16 DI (0x6000), 16 DO (0x6200), 2 AI (0x6401), 2 AO (0x6411), 0x1010/0x1011, 0x1014 (EMCY producer), 0x1020, LSS supported, writable PDO mapping. The simulator's CiA 401 default behaviour loops outputs back to inputs, which the demo uses. Its name and identity must not match any real product (public banned-word guard).

### CI
A new job in `local-runtime.yml` (which already builds the image and has STruC++): `test/virtual-example/run.sh` runs `openplc-canopen-deploy` check and `--export-html`/DCF/DBC on the example, compiles the program with STruC++, deploys with `--runtime local`, waits for every configured node OPERATIONAL (node 20 on `host` included), checks the gateway status, and runs every `test` scenario with `openplc-canopen-diag sim test --network` per network with a JUnit report. Path filter: `examples/**`, `docs/tour.md` is docs only and does not trigger it.

## Risks / Trade-offs

- Container timing makes the cyclic drive slower than real; the guide says timing says nothing about a target. The demo uses a 10 ms task, which the CI runner sustains (`sim_cia402_cyclic` already runs at that rate).
- The example uses many features at once; a change elsewhere can break it. That is the point of the CI job, but it adds a few minutes to `local-runtime.yml` runs (not to every PR).
- The editor GUI steps cannot be checked in CI; the guide's editor chapter is checked by hand on Windows and macOS (hardware-free tasks at the end).
