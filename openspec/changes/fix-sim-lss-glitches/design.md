## Context

Three glitches from the 2026-10-10 bench run (add-cia309-gateway task 9.4). The root causes below come from reading the simulator and the Lely sources at the pinned commit (`tools/deploy/canworks/_lely_dcf/VERSION`). Each one gets a test that fails before the fix (tasks 1.x).

## Root causes

### 1. No LSS answer after `forget-node-id`

`SimDevice::ForgetNodeId()` sets the pending node ID to 0xFF and resets communication. That part works: after the reset Lely's active and pending node IDs are both 0xFF and the NMT state stays in reset communication (Lely's state 7, shown as "unknown" by `sim status`). The plugin's `lss_watch` lets Fastscan through because the device has no valid node ID.

The device still does not answer. Lely creates its LSS slave service only when the device says it supports LSS. In `nmt_srv.c`, `co_nmt_srv_init_lss()` returns at once when `co_dev_get_lss()` is false, and that flag is read from `[DeviceInfo] LSS_Supported` in the EDS. Many EDS files leave it out or set it to 0, including the repo's `cpp-slave.eds` and `servo402.eds`. A config node's simulated device built from such an EDS has no LSS slave at all. Nothing answers the Fastscan's first frame (the "any device without a node ID?" check, bit check 0x80), so Lely's master ends the scan after one LSS timeout (about 0.1 s) with `timed_out`. The plugin reports that as "none found". The standalone device was found because its EDS says `LSS_Supported=1`. A full search takes 13 s because it runs about 128 steps, each one LSS timeout.

The master's side is not involved. The same fastscan path found the standalone device, and the in-plugin device gets the master's frames through its own SocketCAN socket (loopback), like every other request it answers. For a device that does not support LSS, not answering is correct. The glitch is that the simulator let such a device lose its node ID at all. A real device without LSS cannot end up like that: it has DIP switches or a fixed node ID. The same applies when the simulator starts such a device without a node ID (`--node 0`, an extra device with node 0, a simulated node with `lss.assign`). The device can never get a node ID, and the simulator says nothing about it. The configuration has a matching gap: an `lss` object on a node whose EDS has no LSS is only a warning today (`eds_check.cpp`, `contract.py`). The configurator offers the LSS boxes for such a node with a warning. The online LSS operations do not look at the node's EDS at all.

### 2. `fault 70` not found after LSS

`Simulator::Find()` matches only the configured node ID (`spec.node`, 0 for a device started without one) and an extra device's name. `sim_status` already reports the current node ID (`node_id` when it differs, printed as "now node 70"), but the lookup never reads it. The plugin's sim control (`canworks-diag sim`) and scenario steps go through the same `Find()`, so they have the same gap.

### 3. `emcy 0x0000` sends nothing

The fault calls `SimDevice::SendEmcy()`, which calls Lely's `Error()`, which calls `co_emcy_push()`. `co_emcy_push()` refuses error code 0 (`ERRNUM_INVAL`, "not an error"), and the return value is ignored. The fault is still logged and kept as active. `clear emcy` / `clear all` call `co_emcy_clear()`, which sends the error reset only when Lely's error stack has entries. That is why the clear works after an earlier EMCY and does nothing on a clean device. Nothing deliberate is behind this: CiA 301 defines code 0000 as "error reset or no error", and a device sends it with its current error register.

## Decisions

- **No LSS anywhere for a node whose EDS has no LSS.** One rule: a node whose EDS does not say `LSS_Supported=1` in `[DeviceInfo]` (0 or left out, as Lely reads it: `co_dev_get_lss()` is 0) does not support LSS. Nothing in the toolkit uses LSS on it.
  - **Configuration.** The plugin's config check (`eds_check.cpp`, where the warning is today) and the deploy tool's (`contract.py`) reject any `lss` object on such a node, real or simulated, even `{}`. The message is "node N (name): 'lss' needs an EDS with LSS_Supported=1; this node's EDS has no LSS". The same rule covers a slave network with `node_id: null` on an EDS without LSS ("slave: node_id null needs an EDS with LSS_Supported=1; its EDS has no LSS"), which is a warning today too. The shared case `test/fixtures/config/cases.json` changes from accept-with-warning to reject. The configurator's own check comes from `contract.py`, so it reports the same problem.
  - **Configurator.** For such a node both LSS checkboxes are disabled and unticked, with the reason next to them. A loaded node that still has `lss` shows the problem and offers to remove it. "Use for node..." lists such a node disabled with the reason. "Add as node" after an LSS set node ID (online and commissioning) adds the node without `lss.assign` when the matching EDS has no LSS, and says why.
  - **Online LSS operations.** In `Network::DiagLss()`, the one place every client goes through (configurator Online, `canworks-diag`, the CiA 309-3 gateway's `lss_*` requests via the hub), an operation tied to a configured node without LSS is refused with that node's message before any frame is sent. An operation is tied to a configured node when its LSS address has the node's EDS vendor ID and product code and its `serial_number`, or when Set node ID asks for that node's node ID. Vendor and product code alone are not enough. Several EDS files share them (the repo's `cpp-slave.eds` and `lss-slave.eds` are both 0x360/0), and a found device that answers LSS is not that node. Find (Fastscan) and operations on addresses that match no configured node this way stay as they are. The PC-side local bus backend (`localbus/lss.py`) has no configured nodes unless given `--config`. It is left unchanged.
  - **Simulator.** It never adds an LSS slave to such a device. `forget_node_id` on it is refused before the device is touched: "node N: its EDS has no LSS (LSS_Supported=0), so it could never get a node ID back". The refusal reaches the caller (control protocol, `canworks-sim fault`, `canworks-diag sim fault`, a scenario step; exit 1 on the command line) and the log, and the device keeps its node ID and state. A start-up `forget_node_id` in the simulation file and an extra device with node 0 are refused when the simulator starts (`Simulator::Start()`, which the plugin and the standalone simulator both run, so the standalone `--node 0` too) and by the PC tools' `simfile.py`, with the same reason (an extra device is named by its name). A simulated node with `lss.assign` never reaches the simulator, because the configuration check already refuses it. The engine keeps the EDS flag per device (`Dev::lss_supported`, read in the same parse that fills `objects`).
  - Alternatives considered: give such a device an LSS slave anyway (first proposal), or only refuse in the simulator (second). Both were rejected in review: an EDS with `LSS_Supported=0` describes a device without LSS, and no part of the toolkit should treat it otherwise.
  - If the bench device's EDS did say `LSS_Supported=1`, this would not explain it. Task 1.1 therefore also tests `forget_node_id` plus Fastscan on an EDS with the flag. If that test fails, the cause is elsewhere and gets its own fix in this change.
- **NMT state name.** `nmt_name()` and the log name the reset communication state of a device without a node ID "no node ID" (status JSON `"nmt": "lss"`, printed "no node ID, waiting for LSS"), so the status no longer says "unknown" or a bare 7.
- **Lookup order.** `Find(ref)` checks the configured node IDs and the names first, then the current node ID of a powered device (`dev->node_id()` 1-127). A configured node ID always wins: it is the stable key the configuration and the simulation file use. A device found by its current node ID keeps its configured node ID and name. If a powered device's current node ID equals another device's configured one, the request goes to the configured device. That is a node ID conflict, which the status shows. The error for an unknown number stays "node N is not simulated".
- **EMCY code 0.** `SimDevice::SendErrorReset(reg, msef)` empties Lely's error stack and 0x1003, sets 0x1001 to `reg`, and sends one frame (code 0000, `reg`, `msef`) on the 0x1014 COB-ID through the device's send hook, so power and other faults still apply. If the stack had entries, the reset frame Lely's `co_emcy_clear()` sends is suppressed by a one-shot filter in the send hook (EMCY COB-ID, code 0), so exactly one error reset frame goes out. The engine stops a periodic EMCY and drops the active `emcy` fault, like `clear emcy`. The device must still have 0x1014. `period_ms` with code 0 is refused in the file check and the control protocol ("emcy: code 0x0000 is the error reset; it takes no period_ms").

## Risks

- A config that has `lss` on a node with an EDS without LSS was accepted with a warning and is now rejected. Deploy and PLC start refuse it with the message, which names the node and the fix: an EDS that says `LSS_Supported=1`, or no `lss`. Many EDS files leave the flag out although the device supports LSS. For them the user corrects the EDS (the configurator's EDS library keeps the edited copy), and docs/config.md says so in place of today's "warning, not an error" note. The repo's examples are checked: none has `lss` on an EDS without LSS (the virtual plant's `new_io` uses `dio16.eds` with `LSS_Supported=1`).
- The one-shot EMCY filter must not drop a later genuine error reset. It is armed only for the duration of the synchronous `co_emcy_clear()` call. If the EMCY inhibit time (0x1015) holds Lely's frame back, the filter stays armed until that frame goes out, and then disarms.
