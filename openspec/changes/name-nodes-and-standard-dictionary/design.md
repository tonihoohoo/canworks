## Context

- The Nodes table of Commission (`commNodeTable` in `commission.js`, and the with-config table in `app.js`) fills the Device column only from `S.scanResult`. Nodes that are only heard have an empty cell. The scan itself already reads 0x1018:1-4, 0x1000 and 0x1008 per node, both in the PC-direct client (`localbus/client.py` `_scan_one`) and in the plugin (`network_diag.cpp`), and returns `device_name`.
- Manual SDO reads (`/api/online/sdo_read`) work on both connection kinds without force or Allow changes.
- The Object dictionary, Parameters and SDO panel get their objects from `nodeSource(id)`: the config node's EDS, or an EDS opened for a scanned node (`S.onlineEds`). Without one, `odPanel` and `paramsPanel` show `noEds(id)` and `sdoPanel` shows an empty picker. `params.py` builds `od_entries` from a parsed EDS (`ctx.eds`).
- Built-in notes for CiA 301, 401 and 402 already exist in `builtin_notes/` and are merged by object index, so standard objects get their notes for free.

## Decisions

1. **Identity read per heard node, driven by the page.** A new `/api/online/identify {node, port}` reads, in this order, 0x1018:1 (as the probe; a timeout or abort ends it with `answered: false`), 0x1018:2-4, 0x1000, 0x1008, 0x1009, 0x100A, each with the scan's per-read timeout, through the connection's manual SDO read. It returns the same fields as a scan entry (`vendor_id`, `product_code`, `revision_number`, `serial_number`, `device_type`, `device_name`, plus `hardware_version`, `software_version`) and `eds_matches` from the EDS index. The server keeps the answer per connection and node; the status answer carries it so a second page or a reload does not read again.
   The page asks for one node at a time: a node heard for the first time, a node seen booting (boot-up message or state change from not answering), and a node leaving STOPPED whose identity is still missing. A scan result for a node replaces its identity record and counts as read. Strings are decoded as the scan does (latin-1, trailing NULs cut) and shown as text, never as HTML.
   Alternatives: reading in the status poll on the server (hides the work from the page, harder to test, runs even with no page open); running a full scan automatically (probes 127 IDs and asks for force on a running bus).
2. **Device text fallback order.** 0x1008 → product name of the first EDS match → profile name from 0x1000 low 16 bits (301 → "CiA 301 device", 401 → "CiA 401 I/O device", 402 → "CiA 402 drive", 404 → "CiA 404 measuring device", 406 → "CiA 406 encoder", 418/419 battery and charger; any other → "CiA <n> device") → "vendor 0x… product 0x…". The muted line after it gives whatever of vendor (with the EDS VendorName when matched), product and profile is not already the main text. The full name is kept; the cell wraps rather than cutting it.
3. **Standard dictionary as EDS files.** `builtin_od/cia301.eds` holds the CiA 301 communication objects (0x1000-0x1029 that CiA 301 defines, 0x1200 server SDO, RPDO and TPDO 1-4 communication and mapping objects) with their CiA 301 names, data types, access and PDO mappable flags, and no defaults (`DefaultValue` empty: a standard has no single default, so "≠ default" marks never show). `cia401.eds` and `cia402.eds` hold the standard profile objects. The server joins 301 with the profile file that 0x1000 names into one EDS text (writing `[DeviceInfo]` with `ProductName=Standard CiA 301 objects` or `… and CiA 402` and the object lists) and parses it with the existing EDS reader, cached per profile. So the OD tab, Read all, watch, value formats, notes, editing with range check and the SDO picker all work unchanged. The source sent by the page is `{node, standard: true, device_type, port}`; entries carry `standard: true`.
   Alternatives: a JSON table read by new code (duplicates what the EDS reader does and needs its own tests); fetching the device's EDS from 0x1021 (few devices have it; out of scope).
4. **Variable-length objects.** The standard EDS gives arrays such as 0x1003, 0x1010, 0x1011, 0x1016 and the PDO mapping objects their full sub-entry range. The OD tab shows sub 0 and sub 1 until sub 0 has been read, then sub 1 to the read count; sub-entries past it are hidden, not marked missing. For a configured node with an EDS nothing changes.
5. **Missing objects.** For standard entries, aborts 0x06020000 and 0x06090011 are shown as "not on this device" instead of the generic "not readable" text. A new filter **Hide objects the device lacks** is on by default for a standard dictionary and hides an entry, and an object whose entries are all lacking, once its read said so. **Read all** on the standard dictionary reads sub 0 of each object first and skips the rest of an object that does not exist, then probes RPDO and TPDO 5 onwards (communication object sub 0) until the first that does not exist, adding the found ones to the tree. This keeps Read all on a small device to tens of reads, not hundreds.
6. **Where the EDS still wins.** As soon as a node has an EDS (config, match, pick), its EDS replaces the standard dictionary and the cached entries are dropped; the top line of the standard view offers exactly that. Parameters (Back up, Compare, Restore, Store) need the device's own EDS: the tab says "Back up, compare and restore need the device's EDS" and offers the same EDS pick.
7. **Change EDS… as a menu button in the EDS cell.** One small button after the file name opens a menu (the page's existing menu pattern, keyboard reachable): library matches for the node's identity, **Pick EDS file…**, then **Clear EDS** or, for a node only added from an EDS and not heard, **Remove node**. Changing or clearing updates `S.onlineEds`, `S.onlineEdsName` and `commNodes()` together, drops the node's cached `od_entries`, read values, compare marks and watch list of the old EDS, keeps the selected tab, and writes a Commissioning log line ("EDS of node 23: a.eds -> b.eds"). It changes nothing on the device or in a config. A config node's EDS is not changed here: with a config, Configure's node page owns it and the existing **Use matching EDS** in the Compared cell stays the way to swap it from Commission.
8. **No change to the plugin, contract or deploy.** The runtime path already answers manual SDO reads for any node, configured or not.

## Risks / Trade-offs

- Identity reads on a bus with another master can meet that master's own SDO traffic to the same node (both use 0x600 + node ID). This is the same risk as a manual read today; reads are few, one at a time, and a timeout leaves "no SDO answer" with a **Read again** link, nothing more.
- A device that answers 0x1008 with a long or odd string (non-printable bytes): control characters are replaced and the text is shown in full but wrapped; the scan already accepts such strings.
- The standard dictionary can show objects a device lacks until they are read. The top line says so, and Read all hides them.
- Writing through the standard dictionary uses CiA 301 types and access, which a device may define more narrowly; the device's abort is shown as today.
- Built-in EDS files must stay free of vendor or device names (public repo guard); they only hold CiA standard object names.
