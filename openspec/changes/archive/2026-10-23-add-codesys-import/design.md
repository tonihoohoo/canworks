## Context

Today: `codesys/plan.py` turns a config into a plan + node DCFs; `codesys/script/import_canworks.py` (IronPython 2.7 and CPython 3, tested against `tests/fake_codesys.py`) finds or adds the CANbus and manager, then for every planned node removes the node with that node ID and adds it again from its DCF, sets plan parameters by id and names channels. `codesys/run.py` finds CODESYS, its profile, and runs a script headless. The configurator has the CODESYS target, the `.project` file dialog and `codesys_found()`.

Findings from four runs on CODESYS V3.5 SP22 P4:
- All settings are on `connectors[].host_parameters`; `device_parameters` is empty.
- CANbus: 0 bit rate (kbit/s), 2 network number. Manager: 288 node ID, 256/257/258/259 SYNC, 272/273/274/275 heartbeat, 261/262/263 start options, 290/291 TIME.
- Node: communication objects at `index << 12` (`0x01800000` TPDO1 struct {COBID (bit 31 disabled), TransmissionType, PDOParameterAvailable, InhibitTime, EventTimer}, id+1 generic COB-ID string, id+2 processed by manager; `0x0100C000` guarding; `0x01014000` EMCY; `0x01017000` heartbeat producer); object entries at `0x10000000 | index << 12 | sub << 4` (mapping `0x11A00010` {Index, SubIndex, length}, channel at id+1; heartbeat consumer `0x11016010..`; identity `0x11018010/20/30`); param 2 General flags {DCF write, create all SDOs, optional, no init, reset node}; SDO list `0x20001000` rows {Index, Subindex, Value, Size, AbortIfError, JumpToLine, Line}, generated rows first and regenerated by CODESYS after every change.
- PLCopenXML: whole tree, `ParameterId`s, values per element, `<Mapping>` variable names, `<Custom><ImplicitSDO/></Custom>` on generated SDO rows, `download="false"` on an identity parameter = check off.
- In place, public API: values of existing parameters and elements, `io_mapping` variable and manual address, `rename`. Internal only (`PerformWithWriteableCopy` by reflection, `AddParameter(xml)`, `RemoveParameter(id)`, `SetDownload`): adding/removing mapping entries and channels, resizing the SDO list, identity-check ticks.
- Catches: an enabled PDO's struct COBID write is ignored (write the generic string); a node ID change moves only `$NODEID`-based COB-IDs; channels don't follow PDO enable or entry length; manual address must be set while automatic is on; two nodes of one EDS share one repository device id (only the last DCF is kept).

## Goals / Non-Goals

**Goals:** import a CODESYS CANopen manager network into canworks with nothing silently dropped; build back without losing CODESYS-side settings; edits in canworks touch only what changed.

**Non-Goals:** PLC programs, CODESYS as a CANopen slave, J1939 Manager, safety devices, writing PLCopenXML into CODESYS, live sync while both tools are open.

## Decisions

1. **PLCopenXML is the only import format.** One reader (`codesys/xmlimport.py`, CPython, stdlib `xml.etree`) for both routes: a `.project` is first exported headless by a small fixed script (`export_canworks_xml.py`, runs `export_xml` on the chosen device or on every device holding a manager, writes a list of devices too); a hand-exported `.xml` goes straight in. Alternative considered: a script that dumps parameters as JSON. Rejected: it cannot tell user SDO rows from generated ones and needs CODESYS on the PC for every import.
2. **Reader maps by parameter id, not by name** (CODESYS shows names in the user's language). Unknown parameters are ignored; known ones with unexpected shapes become "not carried" lines.
3. **What a node gets:** `node_id`, `name` (CODESYS object name made a valid identifier; original in `codesys.device`), `mandatory` (from optional flag), `boot` (false from no-init), `restore_configuration` (from reset node + its sub-index), `heartbeat_ms`, `heartbeat_consumer`, `guard_time_ms`/`life_time_factor`, `vendor_id`/`product_code`/`revision_number` with the check ticks in `codesys.checks`, `tx_pdos`/`rx_pdos` (number from the communication object, COB-ID, transmission, inhibit, event timer, enabled, entries with `name` from the channel variable), `sdo` from rows without the implicit marker (with `codesys` {abort_on_error, jump_to_line} when set). Bit channel variables become the entry's `bits`.
4. **EDS per node,** in this order: the config's EDS library by vendor/product/revision (exact, then same vendor+product with the nearest revision and a warning); the DCF/EDS in CODESYS's device repository (`<Devices>\<type>\<id>\<version>\*.dcf|*.eds`) when the import runs on that PC, copied into the config folder; else the preview marks it missing with **Add EDS…** and the config is written only after every node has one. A repository DCF that canworks itself wrote is accepted (it is an EDS with values).
5. **Values equal to the EDS default are not written to the config** (project rule: unset means EDS value), except PDO settings, which canworks always lists per PDO.
6. **Carried CODESYS settings** live in `codesys` objects (node: `device`, `checks`; PDO: `by_manager`; entry: `address`; startup SDO: `abort_on_error`, `jump_to_line`). The relevance table marks them CODESYS-only, so the bridge target warns and ignores them, and a target switch to the bridge offers Remove as for other CODESYS fields.
7. **Build updates in place.** For each planned node with an existing project node of the same node ID: read its parameters, compute differences against the plan, write value differences through the public API (generic COB-ID string for COB-IDs, struct elements otherwise), then variable names and manual addresses. Structural difference (mapping entry count, entry length, PDO enabled with channel set change, SDO user rows added/removed/reordered) → replace that node from its DCF (today's path) and write carried settings after it. Identity ticks → internal API in a guarded helper; failure gives a report line naming the ticks to set by hand. Alternative considered: internal API for all structural edits. Rejected as the default because a CODESYS update could break it; the helper stays narrow.
8. **Nodes removed in canworks:** the plan lists the node IDs canworks manages (`codesys.managed` on the network, written by import and build). A project node with a managed node ID that is no longer in the config is removed only when the build dialog's "Remove N nodes" is confirmed; nodes canworks never managed are kept, as today.
9. **COB-IDs:** the plan writes `$NODEID+16#…` when the config's COB-ID equals the EDS's node-based default for that node, otherwise the literal value.
10. **Shared device id:** nodes of one EDS share one repository entry, so a replaced node reinstalls its own DCF right before it is added (as today) and the import never trusts the repository DCF for per-node values (they come from the XML). Documented in docs/codesys.md.

## Risks / Trade-offs

- [Parameter ids or XML shape differ in other CODESYS versions or vendor IDEs] → reader is driven by a table of ids with SP22 fixture tests; unknown shapes become "not carried" lines, never silent loss. Toni's display project (vendor IDE) is a later check.
- [Internal API for identity ticks breaks after a CODESYS update] → guarded, reported, nothing else depends on it.
- [In-place diff misses a setting CODESYS derives from another] → after writing, the script reads the node back and compares with the plan; any mismatch is a report warning.
- [Manual I/O addresses shift other automatic addresses] → CODESYS reassigns automatic addresses itself; the program uses variable names, so this is not reported.
- [Import of a big display project with many devices] → device picker, preselect the active application's device.

## Findings while building

- A PDO that is off is left out of the import: canworks switches off every PDO a node does not list.
- PDO settings equal to the EDS default are left out too (transmission type always written), as for other settings; this keeps an imported config as short as a hand-written one.
- CODESYS maps every mapping sub-entry with a non-zero value, whatever the count says, so the DCFs for CODESYS zero the sub-entries beyond the count (codesys-export "DCF mapping as CODESYS reads it").
- The manager's TIME producer is on when parameters 290/291 are downloaded (their `download` flag), set through the same internal API as the identity ticks.
- User startup SDO rows are the rows for objects from 0x2000 (CODESYS writes them as non-implicit rows from the DCF's ParameterValue); communication objects below come from their own parameters.
- An entry's CODESYS variable that is no valid canworks name is kept in `codesys.variable`.
- The configurator puts Import from CODESYS… on the start page and on the CODESYS page (it has no File menu). Add EDS… gives the EDS to every node of that CODESYS device type.
