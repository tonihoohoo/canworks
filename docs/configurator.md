# Configuring CANopen in a browser: `canworks-config`

`canworks-config` edits a canworks config in a local web page: the CAN adapter, the master, the nodes with their supervision settings, the PDO mapping to PLC addresses, and the startup SDO writes, and also [J1939 networks](#j1939-networks) with their parameter groups. The config runs on [canworks-bridge](modbus-bridge.md) on a Linux device (for OpenPLC or any Modbus client) or is built into a [CODESYS](codesys.md) project. In an OpenPLC editor project it writes the project's `canworks/` folder and the editor's remote device and programs ([OpenPLC editor files on save](#openplc-editor-files-on-save)); the stock editor itself is not changed.

It runs on the engineering PC, next to the editor, and needs Python 3.11 or newer and a browser. It listens only on `127.0.0.1` and loads nothing from the network. The only connections it makes are to the bridge you name for [online access](#online-access), from the moment you connect (the Commission workspace, Simulation or a [trace](#trace) recording) until **Disconnect**, and to a CANopen simulator you name in the [Simulation view](#simulation-view).

## Install

It comes with the deploy tool, in the same package. Install it without Python using uv (Windows, macOS and Linux steps in [install-pc.md](install-pc.md)), or with `pipx install ./tools/deploy`.

Without installing: `PYTHONPATH=tools/deploy python3 -m canworks.configurator.server --help` (needs `python3 -m pip install jsonschema`).

## Start

```sh
canworks-config                                   # start page
canworks-config ~/Documents/workspace/rtd-monitor # open a project directly
```

Or open the **canworks configurator** shortcut: in the Start menu and on the desktop on Windows, in `~/Applications` on macOS, among the applications on Linux. The one-line PC installer adds it ([install-pc.md](install-pc.md#one-line-install-or-update)); `canworks-config --create-shortcut` adds it by hand and `canworks-config --remove-shortcut` removes it. It starts the configurator with no terminal or console window; the process the shortcut starts is the configurator itself, so it starts no second Python.

`canworks-config` starts the configurator in the background, prints its address, asks the default browser to open it and gives the prompt back at once, without waiting for the page: the terminal can be closed. The configurator's messages go to `configurator.log` in its settings folder (`%APPDATA%\canworks` on Windows, `~/Library/Application Support/canworks` on macOS, `~/.config/canworks` on Linux), kept to 1 MB plus one older file (`configurator.log.1`). When no browser opened the page within 15 s, the configurator writes the address to the log and, when started from the shortcut, shows it in a message window to copy it from (from a terminal it is already printed there). Each start also logs one line with the time of each step since it was launched, for example `start timing: python 140 ms, listening 420 ms, browser asked 450 ms, page 1310 ms (from shortcut)`; a terminal start adds `background`, the start of its background configurator.

The configurator stops when its last tab is closed: about 10 s after the tab closed or the browser quit (a reload comes back sooner and keeps it). A page that stops answering without closing (a locked screen or a background tab whose timers the browser stopped, a crashed browser) counts as closed only when it had nothing unsaved, and then only 60 minutes after its last answer; a page with unsaved changes never times out, so they can still be saved when it answers again. Time the PC slept does not count. When it stops by itself its log ([Start](#start)) says why: `its last page was closed`, `its last page sent no heartbeat for 60 minutes`, or that no page was opened. When a tab comes back (shown again, focused, or from the browser's back and forward cache) it asks the configurator at once whether it still runs; when two asks 2 s apart get no answer, the tab says **canworks-config is not running any more** and how to start it again (the **canworks configurator** shortcut, or `canworks-config` in a terminal, which opens a new tab). With unsaved changes it says they could not be saved and offers **Download canworks.json**: the page's config with its changes, to put in the config folder and open in a new configurator. It does not hold EDS and notes files imported since the last save, or the simulation's unsaved edits. Closing or reloading the tab first asks whether to leave the page; browsers ask this in their own words, and only after something was clicked or typed on the page. A configurator whose page was never opened stops after 10 minutes. Stopping closes every connection as **Disconnect** does, so a USB adapter is free for other tools at once. **Quit** at the right of the header stops it from the page, on the start page too: it always asks first (**Save and quit**, **Quit without saving** or **Cancel** with unsaved changes), and says when an adapter connection, cyclic sends, a trace recording or a PDO test will stop with it. The tab then says the configurator has stopped and can be closed.

Started again while it runs, `canworks-config` (or the shortcut) opens a new tab on the running configurator and returns, so there is one configurator per user; with a folder (`canworks-config PATH`) the running configurator opens that folder, and asks first when the open config has unsaved changes. A running configurator is found through `instance.json` in the settings folder, readable only by its user; another user on the same PC gets a configurator of their own. `--new-instance` starts a separate configurator anyway; each one keeps its own session in the same browser.

It stays in the terminal instead, printing its messages there with Ctrl-C to stop it, with `--foreground`, and by itself with `--no-browser` (only prints the address), with `--keep-running`, in an SSH session and on Linux without a desktop (no `DISPLAY` or `WAYLAND_DISPLAY`), where the printed address is the way in. `--keep-running` keeps the configurator running with no page open, until Quit or Ctrl-C, for scripts and remote use. Scripts that relied on `canworks-config` staying in the foreground pass `--foreground`.

The address looks like `http://127.0.0.1:53412/?code=…`. The code in it works once: the configurator swaps it for the session key, kept in a cookie for that browser, and then forgets it, so the session key itself never appears in a URL or the browser history. The page cannot be used without it, so open the printed address rather than typing it; one that was used already is refused (start `canworks-config` again for a new one).

The start page says what the tool is for and has two buttons, a link and the list of recent folders:

- **Open…** picks a folder in the folder dialog and opens it as what it is. The dialog tags each listed folder that is an **OpenPLC project** or holds a **canworks config**; a click selects a folder (**Use this folder** opens it), a double-click or Enter goes into it. A folder with `project.json` opens as an **OpenPLC Editor project**: the config is `<project>/canworks/canworks.json`, and every address is checked against the rest of the project. A folder with `canworks.json` opens as a **config folder**: a plain folder with the config and its EDS or DBC files, for a bus set up before its OpenPLC Editor project exists (the checks against a project are skipped, and the page says so). A folder with neither offers to start a new config there.
- **New config…** asks first what runs the CAN networks: the **Modbus bridge** (preselected; canworks-bridge runs the networks and serves Modbus TCP registers, and works with OpenPLC, truST, other PLCs, Node-RED, and HMI, SCADA or scripts, added later as [connections](#connections)) or **CODESYS** (a CODESYS PLC runs the CANopen master). Then it asks for a name (the folder: a new one, or an existing one without a project or config in it) and where it goes. **Create** writes the target's empty config to disk at once, so a reload shows the new config with its target and **Saved**. A new config's CANopen network runs at 500 kbit/s with SYNC off. A new CANopen network without nodes is one warning in **Problems**, not an error: its Bus page says **No nodes yet** with **Add node…**. A missing or slashed name is shown under the **Name** field, which gets the focus. For OpenPLC, **Add connection → OpenPLC** on the Modbus bridge page offers **New editor project…**, which makes a new OpenPLC Editor project with the config in its `canworks/` folder (while the editor creates it the dialog shows **Creating the editor project…**; on Windows no console window opens for it; an existing folder can become the project when it has none of the editor's files (`project.json`, `devices/configuration.json`, `devices/pin-mapping.json`, `pous/programs/main.st`) and no `canworks.json` or `canworks/`, its other files are left alone, and when creation fails only what it added is removed), and **Move into project…**; it is greyed out with the reason when the editor's `openplc-cli` is not found. A folder that already has a config or is an editor project is refused, with an offer to open it instead.
- **Commission a device without a config** opens **Commission a CANopen device**: no project, no config and no OpenPLC runtime, for a device on the bench through a USB CAN adapter on this PC. See [Commission a CANopen device](#commission-a-canopen-device). Nothing is added to a config, and the scratch folder it uses is not listed among the recent folders.
- **Install on a device** opens the [Devices](devices.md#without-a-config) workspace with no config, to install the Modbus bridge, its remote link and local network discovery on a Linux device over SSH, or to turn on its remote CAN adapter. **Close** goes back to the start page.

**Recent** lists the folders opened last, each with its target (Modbus bridge or CODESYS), whether it is an editor project or a config folder, and when it was opened; one click opens it, and **Remove** takes it off the list (the folder stays). A folder is added to the list once it opened. With nothing in the list, four starting points take its place: open an OpenPLC project, start something new, talk to a device, or set up a Linux device. A folder the configurator cannot read, or a save where it cannot write, ends with a message naming the folder and the reason, and the page stays where it was. A path given on the command line opens directly: as a project when it has `project.json`, as a config folder otherwise.

## The page

The page has three workspaces. **Configure** edits the config: the [network tree](#network-tree) on the left leads to its pages. **Commission** works on the live bus through the bridge: its **Nodes** page is the [online view](#online-view). **Devices** installs what the project needs on a Linux device over SSH; its device list is the same for every project and for the start page's **Install on a device** ([devices.md](devices.md)). **Configure | Commission | Devices** at the top of the page switches between them; the draft, the connection and the running jobs stay as they are, and the workspace comes back after a reload. Links to a page of the other workspace (a problem, **Back to the online view**) switch to it.

The header has, from left to right, the workspace switch, the config's folder with **● unsaved** while there are unsaved changes, a **Simulated** chip while the config has a simulated network (its **ⓘ** says what is simulated and that the config is not to be uploaded as it is), **Settings** (the theme), **Reload from disk**, **Close** (back to the start page), the **Export** menu (see [Where things are](#where-things-are)), the target's one hand-off button (**Build into CODESYS project…** in a CODESYS project, **Install on device…** in a Modbus bridge project), and **Save**. In a window under 1500 pixels wide with a config open, **Reload from disk**, **Close**, **Settings** and **Quit** move into one **⋯** menu so the header stays one row; with no config open (the start page, Devices without a config) they stay buttons. From 1280 pixels the header is one row for every target; when it would wrap, the simulated chip says only **Simulated** (its tooltip and **Details** keep the rest), and a menu opens inside the window. Under 1100 pixels the page title is hidden, the folder's name is shortened (its path stays in the badge's tooltip) and the unsaved mark is just **●**. The folder's badge ends with the project target (**· Modbus bridge** or **· CODESYS**), which opens the [Project page](#project-target). Under it, tabs lead to the workspace's own page and its tools, each tool in one workspace: **Network** and **Simulation file** in Configure; **Nodes**, **Simulation** (live), **Trace** and **Frame lab** in Commission. A link to a tool of the other workspace (a problem, **Explain in Frame lab**, **Send…**, **Edit the simulation file**) switches workspace. A tool uses the whole width of the page, with no tree. The network a Commission tool works on is picked in one place, the connection bar's network picker, which shows the config's networks even before connecting.

The **connection bar** sits at the right end of the tab row (on a second line only when the row is too narrow) and is the one place to connect and disconnect. It shows always in Commission, and in Configure while connected: the runtime, the CANopen simulator or the USB adapter, the path and round trip to a runtime (`LAN`, `internet direct`, `internet relayed`; amber above 100 ms, red above 300 ms) or the adapter's bit rate and how it was confirmed, the network picker when the config has several networks (the only one: Trace and the Frame lab use it too), the bus state and counters, another master when one is seen, whether changes are allowed, and **Connect…** or **Disconnect**. It has no colour while all is well, turns amber for a warning (error passive, a round trip above 100 ms) and red for a fault: an ended or lost connection (with the reason, or the age of the last data while retrying, and **Change…** to pick another runtime), bus-off, another master or a round trip above 300 ms. **Connect…** opens the connect panel, the only place to connect; no page has a connect form or button of its own, and a page without a connection says in one line what it needs one for. The panel lists up to three recent connections of this PC first, one click each (the newest has the focus, so **Connect…** then Enter reconnects), then the form: a runtime or a [CANopen simulator](#simulation-view) for a config ([Online access](#online-access)), a USB adapter in [Commission a CANopen device](#commission-a-canopen-device), and in both an [adapter on another machine](pc-adapter.md#an-adapter-on-another-machine). One connection is open at a time. The connection stays open on every page and tool until **Disconnect**, which also stops the trace recording, the Send panel's jobs, a scan and the PDO test on it. Entering Commission connects at once when this PC has the runtime host and the token; otherwise the focus is on **Connect…**.

The **status bar** at the bottom lists the running jobs on every page: a scan, LSS find, Read all, back up, compare, restore, write configuration, a trace recording, the PDO test, SYNC from the PC and cyclic sends, each with its progress and **Cancel** (LSS find ends by itself within about 15 seconds and has no Cancel; cancelling a restore or a write configuration asks first). While connected to a USB adapter it also shows the frame rate and an estimated bus load. Above it, the **bottom panel** holds **Problems** in Configure (open while there are problems and a one-line strip with its count while there are none; it remembers when you close it) and in Commission (a one-line strip), and the commissioning **Log** in Commission a device.

In **Commission a CANopen device** nothing edits a config: no workspace switch, no Export menu, no Save and no Problems; the tabs are **Nodes**, **Trace** and **Frame lab**.

Everything works from the keyboard: Tab moves through the header, the tabs, the connection bar, the network tree, the page, the bottom panel and the status bar; Enter or Space opens a node, a problem, a menu item or a row in the scan and simulation tables (in the Nodes table, the node ID button opens the node); arrow keys move between the header's tabs, the tabs of the trace, the online node and the simulation views and between the items of an open menu; Escape closes a menu or a dialog. The focus never drops to the page: when a button goes away or is disabled (after **Connect**, **Scan the bus**, **Add to config**, **Save**), it moves to the control that replaces it or to the nearest one. Dialogs put the safe choice first and give it focus, so Enter never removes or discards anything; the button that does is marked in red.

**Ctrl+Z** (Cmd+Z on a Mac) undoes the last change to the draft, and **Ctrl+Shift+Z** redoes it, whether it was typed into a field, picked from a list or made by a button: a removed node, PDO entry, startup SDO or SDO variable comes back with every setting. The message after a removal also offers **Undo**. Inside a field, the browser's own undo applies until you leave it. The stack starts empty when a config is opened or reloaded.

**Selected rows** look and work the same in every list and table: click anywhere on a row, its buttons included, or tab into it, and the row gets a light wash with an accent bar on its left edge; the row under the mouse gets a lighter tint. Each list has one selected row, kept while the page redraws, a value refreshes or a filter hides and shows it, until the page is reloaded. Esc in the list clears it (in the trace lists and the Frame lab, which explain the selected row, the arrow keys and Esc work as before). The network tree marks its open entry the same way. Status tables and bit grids have no selected row.

**Window sizes.** In a window 800 pixels high or less (a 1920×1080 laptop at 150 %) the header, the tabs, the message bars and the status bar get compact spacing and the bottom panel's lists get shorter, so the page keeps most of the height. From 801 to 1100 pixels wide the network tree becomes a narrow rail of network initials and node IDs with their state and error counts; a click on one opens it, and the rail's **☰** button opens the whole tree over the page. Under 800 pixels the tree is a button that opens it. From 1800 pixels wide, the Bus page and a node's Supervision tab use two columns, and under 640 pixels the PDO entry tables become one card per entry.

**Resize bars** sit under the list boxes: the object pickers of the PDO, Startup SDO writes and SDO variables sections, the slave's objects, the gateway routes, the object dictionary, simulator values and J1939 signals tables, the Frame lab lists, the Modbus bridge's register map and the problems list. Drag a bar, or press Up or Down (40 pixels a step) while it has the focus, to make the box shorter or taller (120 to 3000 pixels); double-click restores the default. Each kind of box keeps its height on this PC (in `ui.json` with the theme), so every node's Startup SDO picker opens at the height you last chose.

### Where things are

One rule places every part of the page:

- The **Project** page holds the project target and what concerns the whole project: the **Editor project** section when the config has an OpenPLC connection or is inside an editor project (the project, or **Move into project…** and **New editor project…** in a config folder).
- The header's primary button puts the config onto the target: **Install on device…** or **Build into CODESYS project…**.
- **Export** holds the network files: **All DCFs**, **This node's DCF** while a node page is open, **DBC** with its SDO choice, **Documentation**, and on a CODESYS config **Download for CODESYS**. A slave network's EDS and device notes are exported from their own pages.
- The **Modbus bridge** page holds the bridge settings and the [connections](#connections), each with its program-side files (register map, ST, PLCopen XML, Node-RED flow and package); the **CODESYS** page holds the CODESYS settings.
- **Copy as ST call** sits on the item it copies (an object dictionary entry, an NMT command, a CAN message, a J1939 PGN), on Modbus bridge configs only: the canworks blocks exist only in a program that talks to the bridge. When the config lacks the bridge part the block needs (the SDO bridge registers, the control block, a request mailbox or the receive mailbox), the button's tooltip and the copied text's first comment name it.

### Colours and icons

The page is grey while all is well; colour marks a state, and every state also has its own shape, so it reads the same in both themes, in grey-scale and in the operating system's high contrast mode. The same icons are used on the network tree, the Nodes table, the node tabs, the connection bar, the status bar, Problems, the message bar and the trace. **Settings → Colours and icons** shows this legend on the page.

| Icon | State | When |
|---|---|---|
| filled circle (green) | Operational | The node runs and exchanges PDOs; the connection is up and the bit rate confirmed. |
| half-filled circle (blue) | Pre-operational | The node answers SDOs but sends no PDOs yet. |
| ring with a gap (blue) | In progress | Connecting, booting, or a job is running. |
| filled square (amber) | Stopped | The node was stopped and only answers NMT and heartbeat. |
| triangle with "!" (amber) | Warning | Something needs a look, but nothing is broken: a warning in Problems, error passive, a slow path. |
| circle with a cross (red) | Error | A missing node, bus-off, an ended connection, an error in Problems. |
| hollow circle (grey) | Unknown | No information: not connected, not heard, or absent from a simulated network. |
| circle with "i" (grey) | Information | A message bar that tells, without asking for anything. |
| small flag after the icon | Diagnosis | Red while an EMCY or error is pending for the node, grey once it is cleared. |
| dashed ring around the icon | Simulated | The node is simulated. Simulation is a mark, not a state, so it has no colour of its own. |

Text in tables and lists stays in the normal text colour; only a warning or an error tints a row. A control that cannot be used says why in its tooltip ("Needs a connection with changes allowed"). Labels and messages follow one word list, [wording.md](wording.md).

## Network tree

The tree on the left is the only navigation of a config, in both workspaces. In Configure it starts with **Project**, the page with the [project target](#project-target) and [Online access](#online-access). Each network is an entry with its name and, on a second line, its protocol (CANopen master, CANopen slave, J1939, Plain CAN). Names are never cut: a long one wraps onto the next line. Under a network come **Bus and master** (**Bus and ECU** on J1939, **Bus** on Plain CAN and slave networks), the slave device on a slave network, the nodes in node ID order, **+ Add node…** (which opens the [Add node dialog](#add-a-node)), **PDO links** and **CAN messages**, as the network has them. After the networks come **Gateway** (when the config has a slave and a master network), **Modbus bridge** (in a bridge project) and **+ Add network…**. Below the tree are the unused EDS files and the address scan line.

Every entry shows its problems as a badge, `2✕ 1⚠` (errors and warnings, read out as "2 errors, 1 warning"); a folded network shows the sum of its entries. A simulated node has a hollow mark and an absent node (switched off on a simulated network) a dashed one. The **⋯** button on a network entry opens its menu: **Rename…**, **Make it a slave network…** or **Make it a master network…** (CANopen networks) and **Remove…** (with more than one network). Which networks are folded is kept on this PC in `ui.json`.

The tree is one Tab stop. ↑ and ↓ move, → unfolds a network or goes to its first entry, ← folds it or goes to its network, Home and End go to the first and last entry, Enter or Space opens the entry, Shift+F10 or the context menu key opens a network's menu, and typing goes to the next entry starting with the typed text (a node ID or a name).

In Commission the tree shows the networks and their nodes only. A network opens its node table with the bus state, a node its live view; picking an entry on another network moves the connection bar's network picker, and the picker selects that network in the tree.

## Node tabs

A node page has its heading, **Export DCF** and **Remove node** above a row of tabs; one tab shows at a time, each with its own problem badge. The open tab stays when you open another node (when that node has it), so comparing one setting across nodes is a click per node, and it comes back after a reload.

| Tab | Holds |
|---|---|
| **General** | node ID, name, EDS and the **Simulated** switch |
| **PDOs** | inputs (TPDOs) and outputs (RPDOs), side by side from 1400 px; each PDO's mapping, and one line summing up its COB-ID, transmission, timers and timeout, where **Settings** opens them (they open by themselves on a problem). Each entry has one name: the **Variable** placeholder is the whole name the OpenPLC variable list and the Modbus map use (`io_rtd_AI0_Input_PV`). An entry with no PLC location (and no bits) says **not mapped to the PLC**, with **Suggest** filling a free location |
| **SDOs** | [startup SDO writes](#startup-sdo-writes) and [SDO variables](#sdo-variables) |
| **Supervision** | heartbeat or node guarding, the heartbeat watch list, status bit, state byte, NMT command, boot error byte, and the EMCY code, error register and EMCY COB-ID |
| **Simulated device** | for a simulated node: its value sources, faults at start and default behaviour from `simulation.json`, the same draft as the Simulation file tab |
| **Notes** | your own [device notes](#device-notes) first (**My notes**, **All notes**, **All objects**), with search, **Note**, **Add note…**, **Import notes…** and **Export notes…**; the tab label counts your notes |
| **Advanced** | the remaining node settings |

Where the sections of the former one-page node view went: Node → General; Supervision and Emergency (EMCY) → Supervision; Inputs and Outputs → PDOs; Startup SDO writes and SDO variables → SDOs; Advanced → Advanced. The section index is gone. Online access, which was a part of the first network's Bus and master page, is on the Project page.

Clicking a problem in **Problems** opens its tree entry and tab, opens a closed part holding the field, and focuses the field.

When an export stops (DCF, DBC, Documentation, Download for CODESYS, or a connection's Download), it says so in **Problems** only: a red bar at the top of the panel names the export and says nothing was downloaded, and its findings are listed under it, each opening its field. Problems opens if you had closed it. The bar goes after your next edit or the next export. A successful export reports in the message bar, with the number of warnings when it has any, and Problems opens with them.

## Bus and master

**Bus and master** holds the CAN adapter: its type ("SocketCAN" for a CAN HAT, a candleLight CANable, PEAK or vcan; "CANable / serial (slcan)" for a CANable with its stock firmware or a Lawicel CANUSB), the interface on the PLC and the bit rate from the CiA 301 list, then for SocketCAN whether the bridge sets up the link and the bus-off restart delay, and for slcan the serial device (`/dev/serial/by-id/...` on the PLC) and the optional serial speed. Switching type keeps the interface and bit rate and drops the other type's settings. Then come the master (node ID, SYNC source, SYNC period, master heartbeat, **When the bridge stops**, EDS lint; **SYNC source** is **Off** (no SYNC, the default) or **Timer** (shows the SYNC period, 10 ms when picked; emptying the period turns SYNC off); without SYNC, **Check** names every PDO that still has a synchronous transmission type), and the optional diagnostic inputs (bus state, TX and RX error counters, bus-off count, the master's own NMT state), each with **Suggest** for a free `%IB` byte or `%IW` word. A file that still uses the old top-level `interface` and `bitrate` keys is shown as an adapter with "sets up the link" off, and is saved in the `adapter` form. **EDS lint** chooses which of `dcfgen`'s EDS lint findings stop the network: **Communication objects** (the default, saved as no field) stops only on findings in 0x1000-0x1FFF that are not only about limits, **Every object** on any finding, **Off** on none ([config.md](config.md#eds-lint)). **When the bridge stops** (`on_plc_stop`, a Modbus bridge config only) is what the master sends to each node that is up when the bridge stops or its network closes: **Pre-operational** (the default, saved as no field), **Stopped** or **Keep running** (nothing); an OpenPLC config has the bridge's **When the writer is lost** instead. A file with the old `strict_eds` is shown as **Every object** (`true`) or **Off** (`false`), and is saved as `eds_lint`. See [config.md](config.md) for what each field does on the bus.

## Simulated network and devices

Two switches choose what is [simulated](simulator.md#two-switches), so a project can be tried without its devices. **Bus and master → Network** is **Real** (the default, no field in the file) or **Simulated** (`adapter.simulate: true`): the master then runs on a virtual bus inside the bridge, with no CAN interface. The adapter settings stay as they are, so switching back is one choice. Each node has a **Simulated** switch on its **General** tab (the node's `simulate`). On a simulated network every node is simulated unless switched off, and a node switched off is shown as **absent**: it stays off the network, as an unplugged device. On a real network a node switched on runs as a simulated device inside the bridge on the real interface, next to the real devices. **Simulate all** and **Simulate none** under **Network** switch every node; the line next to them lists the simulated nodes, and the tree marks each node **simulated** (hollow mark) or **absent** (dashed mark).

A node's `simulate` is saved only when it differs from the network's default (on a simulated network only `"simulate": false`, on a real one only `"simulate": true`), so a file stays minimal. Switching the network sets every node back to that default.

Simulating anything turns online access on with **Allow changes** when it is off, and the message bar says so: the [Simulation view](#simulation-view) needs it to move values and inject faults. When online access is already on, it is left as it is.

<a id="message-bars"></a>**Message bars** look the same everywhere, in four kinds, each with its icon and a coloured edge on the left: **information** (grey edge, the "i" icon), **done** (grey with a green edge and the Operational icon), **warning** (amber tint) and **error** (red tint). Each message sits at the top of what it is about: the page's own bar and the simulation bar under the header, a view's or a section's bars under its heading (the Nodes page's connection line above the scan, a node's stale data above its tabs, a job's result such as a back up or compare at the top of the Parameters tab, the Faults box's result under its title), and a dialog's bars at the top of the dialog (the connect panel's error, "nothing to write" in a restore or write configuration preview, the folder chooser's error). Several bars are listed most severe first. A bar's buttons (**Remove**, **Undo**, **Download**, **Allow changes**) sit on its right. Text about one field stays at that field (a red or amber line under it, a row's error in its table), the empty-state lines stay grey text, and **Problems** and the status bar stay at the bottom; a stopped export's bar is at the top of Problems, not in the message bar. Errors are announced to screen readers as alerts and the other kinds politely, each once; a view's connection line is rewritten only when it changes.

While anything is simulated, a one-line warning bar under the header on every page names it, network by network ("Simulated: io (nodes 5, 6, 7), motion (node 4), cell (slave). Do not upload it to a machine as it is."). **Details** opens the full text: what each network simulates ("The network is simulated: the master runs on a virtual bus inside the bridge, with nodes 5, 6 simulated and node 7 absent.", or "Nodes 5, 7 are simulated on the real network can0.") and that the configuration must not be uploaded to a machine as it is, because a simulated device controls nothing.

A field left empty uses the slave's EDS default or the bridge's default, and the page shows that default in the field and in the hint under it. For the PDO transmission type and the heartbeat period, empty means nothing is written to the slave: it keeps the value from its EDS. Some defaults are worked out from other values: a PDO's COB-ID (CiA 301, for PDOs 1 to 4) from the node ID and PDO number, and the heartbeat timeout as 3 × the heartbeat period. Settings with a fixed set of values, such as the adapter type, bit rate, supervision method and PDO transmission type, are dropdowns that explain each choice.

## Several networks

A device with two or more CAN interfaces can run one CANopen network on each, up to 8 ([config.md](config.md)). **+ Add network…** at the end of the tree asks for the new network's protocol: **CANopen**, **J1939** or **Plain CAN**, each with a line on what it is for (↑ and ↓ move between them, Escape adds nothing). It adds a network with no nodes and no interface, at its protocol's default bit rate (500 kbit/s for CANopen and plain CAN, 250 kbit/s for J1939) and, for CANopen, with SYNC off: enter the interface (each network needs its own; no two `slcan` adapters may share a serial device) and add its nodes. Each network is an entry of the tree, named after its interface (`can0` for example) unless renamed.

Each network's entry holds its **Bus and master** page and its nodes; the heading reads "Bus and master: network `<name>`". A network is named after its interface unless you give it a name with **Rename…** in its menu (**⋯**) (a letter, then letters, digits or `_`, at most 16 characters, unique without regard to case; empty goes back to the interface's name). The name names the network's folder in exports and prefixes its variables. Renaming a network, or changing a node's ID, updates the gateway routes and the gateway's upper network that name it. **Remove…** in its menu asks first, naming the network and its number of nodes; its EDS files stay in the folder. Removing the gateway's upper network removes the gateway with it, and the question says so.

Node IDs, the master's node ID and COB-IDs are per network, so two networks can both have a node 2. IEC locations are not: **Suggest** skips the locations every network uses, and the checks report a location used on two networks, two networks on the same interface or serial device, and duplicate names. With several networks, **Problems** starts each entry with its network ("Network drives, Node 2 drive, ..."), the tab of a network with errors shows their number, and clicking an entry of another network opens its tab.

Saving writes version 2 (`networks` and a top-level `diagnostics`), with one network or several. A version 1 file was made for the removed canworks plugin and opens read-only, with **Use with canworks-bridge**.

## Slave networks

**Role** on a network's **Bus and master** page, or the role item of its menu in the tree, makes the network a [slave network](slave.md): the bridge is one node of a network another master runs. Switching a network with nodes or master settings to **Slave** asks first, because those are dropped (their EDS files stay in the folder); switching back to **Master** asks before dropping the slave settings and starts with an empty master network. A slave network needs `schema_version` 2, so the file is saved as version 2. The page then reads "Bus and slave device", keeps the adapter settings, and has in place of the master settings and the node list:

- **Network**: **Real** (the CAN adapter) or **Simulated** (`adapter.simulate`): the slave then runs on the bridge's simulated bus named by its interface, where a simulated master network with the same interface name reaches it ([slave.md](slave.md#simulated-bus)).
- **Slave device**: the node ID, or **Node ID by LSS** (`node_id: null`, the master's LSS assigns it), the EDS (an [EDS field](#choosing-an-eds): **Choose EDS…** lists the EDS files built here first), **Export EDS**, the inputs when the master is lost (hold or zero) and the EDS lint.
- **Build the EDS**: the object list editor, open by itself while the slave has no EDS. Each object has a name, a type, a direction (from the master: a PLC input; to the master: a PLC output), a default and optional low and high limits; above the list are the device name, vendor ID, product code, revision number (empty: derived from the objects), heartbeat and the layout (manufacturer objects at 0x2000/0x2100, or CiA 401 generic I/O). **Generate EDS** builds the file with the same generator as `canworks-deploy slave-eds`, names it after the device name (`openplc-slave.eds` for "OpenPLC slave"), and offers to bind every generated object to a suggested free location; it keeps the location of an object already bound. The EDS and its description (`<file>.eds.json`, so the editor shows the list again later; a description named `<name>_eds.json`, as for `canworks-deploy slave-eds`, is read and kept under that name) are written to the folder on **Save**. With a description, **Generate EDS** keeps the slave's EDS name. With a [gateway](#gateway), **With the gateway objects** adds the route objects, the status ARRAYs and the SDO bridge record, and writes each route's slave object.
- **Objects**: the bound objects from the EDS, each with its EDS name, type, the direction its `AccessType` gives (`rww`/`rw`: the master writes, an `%I` location; `ro`/`rwr`: the program writes, a `%Q` location), its PLC location with **Suggest** (a free location of the matching area and size) and an optional variable name. **Bind** adds an object of the EDS that is not bound yet. A location of the other area is an error that names the area the object needs.
- **Status and EMCY**: the own state byte, communication OK bit, SYNC count, and the EMCY code and error register the program sends, each with **Suggest**.

**Export EDS** downloads the EDS the bridge runs, byte for byte, named after its device name, for import into the other master's configuration tool. The DCF and DBC exports cover the master networks: **Export all DCFs** with all networks leaves slave networks out, and a slave network's tab offers no DCF or DBC export: its EDS is the file for the other master's tool.

## Gateway

**Gateway** in the tree appears when the draft has a slave network and a master network. Its switch adds the top-level `gateway` ([gateway.md](gateway.md)) with the first slave network as the upper network, or removes it (asking when it has routes). The page has the upper network, a table of **Routes** (a name; a slave object from the upper network's EDS; the field network, node and PDO entry, picked from the config; the direction the entry gives, up for a TPDO entry and down for an RPDO entry), **Add route**, and the options: field node status with its index, EMCY forwarding, what happens when the upper master is lost, and the SDO bridge with its index and whether it may write. The checks report a route whose direction does not fit the slave object's access type, ends of different types, and a target with a second writer; **Problems** names the route. Generate the upper network's EDS again after changing the routes, with **With the gateway objects** ticked.

## J1939 networks

**Protocol** on a network's bus page makes it a [J1939 network](j1939.md): the bridge is an ECU that claims an address and receives and sends parameter groups (PGNs). **Add network** asks for the protocol of the new network; switching an existing network asks first, because its nodes, master or slave settings, or its J1939 settings are dropped. A bit rate still at the old protocol's default becomes the new protocol's default (250 kbit/s for J1939, 500 kbit/s otherwise); a rate you chose stays. A J1939 network needs `schema_version` 2, so the file is saved as version 2. The tree then reads **Bus and ECU**, and **Scan** and **Simulation file** are hidden for that network. **Simulation** stays: the bridge does not simulate J1939, so it gives the `canworks-j1939-sim` command line for the network's DBC file and interface to copy ([j1939.md](j1939.md#simulator)). The page has, below the adapter settings:

- **ECU identity**: the preferred address (0 to 253), the address range the ECU may move to, the claim state and current address inputs with **Suggest**, and the NAME fields. **NAME value** shows the 64-bit NAME the fields make, as the ECU sends it.
- **DBC file**: **Import DBC…** reads a DBC file and opens the message picker; a different file of the same name in the folder asks whether to replace it or keep both (the new one then gets a `-2` suffix). A network has one DBC file, which the trace decodes its frames with, so importing another file on a network that has PGNs from its DBC asks first. **Pick messages…** opens the picker again on the network's DBC file. The picker lists each J1939 message (29-bit identifier) with its PGN, sender, length and signals; set each to **Receive**, **Send** or **Leave out**, and **Add picked messages** adds them as `rx` or `tx` entries, every signal at a free PLC location of the right size. A DBC file without J1939 messages is refused; problems with single messages are listed. The file is written to the folder on **Save**, only when a network names it.
- **Received PGNs (rx)** and **Sent PGNs (tx)**: one block per PGN with its PGN, name and settings (source address or NAME and timeout with the status input for received PGNs; priority, destination for a PDU1 PGN, length, period and least gap for sent ones), and a table of its signals: start bit, bits, byte order, signed, scale, offset, unit, PLC location and, for received signals, the valid input. **Add received PGN**, **Add sent PGN** and **Add signal** add them by hand. **Copy as ST call** copies Structured Text for the program's [J1939 message blocks](j1939.md#program-blocks): for a received PGN a `J1939_RECEIVE` instance with the PGN and source, drained in a `WHILE` loop with a `J1939_GET_BITS` line per signal (scaling as a comment), and a `J1939_REQUEST` call to the source; for a sent PGN a `J1939_SEND` call with a `J1939_SET_BITS` line per signal and a note that the program may send it only once the entry is gone or `raw.program_override_protocol` is set.
- **Requests**: the PGNs the ECU asks for, with the destination and the period.

Signals of multiplexed PGNs have the same **Switch** and **Page** cells and sent PGNs with switches the same **Pages** choice as on the [CAN messages page](#multiplexed-messages); the message picker shows each message's switches and page count, and a message with several switches but no `SG_MUL_VAL_` is listed with a note that its multiplexing cannot be read.

The checks report what the bridge would refuse (addresses, PGNs, signals outside the message, locations of the wrong area or size, a location used twice across all networks); **Problems** names the network, the PGN and the signal. With [online access](#online-access), the online view (Commission → **Nodes**) of a J1939 network shows the claim state, the address and NAME held, the bus counters, the ECUs on the bus, and per received PGN its sources, message count, age, timeout and raw signal values, and per sent PGN the messages sent and requests answered. The trace decodes the network's frames with its DBC file ([j1939.md](j1939.md#diagnostics-and-trace)).

## CAN messages and plain CAN networks

**CAN messages** under a network in the tree holds a network's [raw CAN messages](raw-can.md): plain frames received into `%I` and sent from `%Q`, on a network of any protocol. **Add network** and **Protocol** offer **Plain CAN** (`"protocol": "none"`): a network with only these messages, no master, nodes or ECU. Its bus page reads **Bus** and holds the adapter, and the **Real**/**Simulated** switch; **Scan** and the nodes are hidden. A plain CAN network has **Listen only** on the CAN messages page: the bridge only watches the bus and never sends or acknowledges a frame, so sent messages are refused.

The page lists **Received messages** and **Sent messages** with identifier (hex, `ext` for 29 bits, the mask for received ones), DLC, timeout or period and the number of signals. Click a row to edit it: the message's settings (timeout, status, counter, identifier, DLC and data inputs for received messages; period, on change with least gap, trigger and enable outputs, fill byte and **Override protocol** for sent ones), a table of its signals (start bit, bits, byte order, signed, scale, offset, unit, **Switch**, **Page**, PLC location and, for received messages, the valid bit; see [Multiplexed messages](#multiplexed-messages)) and a **Bit layout** grid that colours each signal's bits and marks overlaps in red. **Suggest addresses** fills every empty location with a free one of the right size; **Copy as ST call** copies a `CAN_RECEIVE` or `CAN_SEND` call for the message with a `CAN_GET_BITS`/`CAN_SET_BITS` line per signal ([raw-can.md](raw-can.md#st-helpers)). **DBC file** names the file the messages came from, or says there is none yet. **Import DBC…** opens the file picker; the file is kept with the draft and written into the config folder on **Save**, and a different file of the same name in the folder asks whether to replace it or keep both (the new one then gets a `-2` suffix). Importing a different file on a network that already has messages from one asks first; its messages stay. The picker lists each message with identifier, DLC, cycle and signals; set each to **Receive**, **Send** or **Leave out** (messages a node named `PLC` or like the network sends start as **Send**, messages the network already has are marked and start as **Leave out**), and **Add picked messages** adds them with free addresses. The file's name is kept as the network's `raw.dbc`. **Pick messages…** opens the picker again on that file; a file the config names that is not in the folder is marked as missing. Removing the last message clears `raw.dbc`. On a CANopen or J1939 network, **Program may send protocol identifiers** lets the frame blocks use identifiers the protocol owns.

The checks report what the bridge would refuse (identifiers, masks, signals outside the frame, a sent identifier the protocol uses without **Override protocol**, locations). The online view (Commission → **Nodes**) adds a **CAN messages** block on any network with raw messages or program frame blocks: frames sent and received, bus load, the program's receivers and cyclic jobs, simulated plain CAN devices, and per received message its count, age or timeout, short frames and last frame, and per sent message its count and last error. A plain CAN network shows its bus row and this block only.

### Multiplexed messages

A message whose frames carry different signals depending on a selector value (DBC multiplexing; [raw-can.md](raw-can.md)) is set up in the signal table:

- **Switch** marks the selector signal (`"multiplexer": true`). A message can have several, and a switch can itself be on a page (nested).
- **Page** holds the switch values a signal is sent with, typed as `1` or `1-2, 5-9` (`"mux": {"values": [[1, 2], [5, 9]]}`); empty means the signal is in every frame. With several switches a dropdown in the cell picks the switch (`mux.on`); with one switch `on` is left out. Rows are sorted with the always-present signals first, then by page.
- **Valid bit** (received messages): a `%IX` input that is TRUE while the signal's page keeps arriving within the timeout (`valid_location`).
- **Bit layout** shows one page at a time: pick it above the grid. The grid shows the switches, the always-present signals and that page's signals, and marks overlaps only between signals that can be in one frame.
- **Pages** (sent messages with switches): **The program picks the page** (`program`, the default; the switch outputs select the page), **Every page each time** (`all`) or **The next page each time** (`rotate`). In `all` and `rotate` the bridge sets the switches, so they have no location: choosing one of them clears the switches' locations, and **Suggest addresses** leaves them empty.

**Import DBC…** keeps the DBC's switches and pages and shows them in the picker; a message with several switches but no `SG_MUL_VAL_` is listed with a note that its multiplexing cannot be read. The online view shows a received message's unknown pages (frames whose switch value has no page) and marks a sent message whose switch outputs select no page.

## Project target

**Project target** on the **Project** page (the tree's first entry in Configure, or the target in the header badge) picks what runs the CAN networks. No Bus, Modbus bridge or CODESYS page has the field:

- **Modbus bridge** ([modbus-bridge.md](modbus-bridge.md)): `canworks-bridge` runs the networks and serves every located value as a Modbus TCP register to the config's [connections](#connections): OpenPLC, truST, other PLCs, Node-RED, HMIs. The config has a top-level `bridge` object; locations are byte addresses.
- **CODESYS** ([codesys.md](codesys.md)): a CODESYS PLC runs the CANopen master networks, built into a CODESYS project. The config has a top-level `codesys` object.
- **OpenPLC plugin (removed)**: shown only for a config made for the removed canworks plugin inside the runtime (one with neither `bridge` nor `codesys`). It opens read-only: the Project page says the plugin was removed, with **Use with canworks-bridge**: it repacks the locations for the bridge, adds `bridge` (inside an editor project with an OpenPLC connection), removes what the bridge does not use (also the CiA 402 `axis`, `sync_source`, `sync_cycles` and the scan watchdogs), and is one undo step. Nothing else changes such a config; the bridge, the deploy tool and the check refuse it.

OpenPLC is not a target: it is a connection of a bridge config. The parts only OpenPLC uses (the Editor project section, the address scan, the connection's poll and editor names) follow the OpenPLC connection.

The page shows only what the target uses. One table in the tools says what each target does without, and the same table gives the check's warnings and the CODESYS report's `not set` list:

| Hidden for | What |
|---|---|
| Modbus bridge without an OpenPLC connection | the Project page's Editor project section (outside an editor project) and the address scan |
| CODESYS | PLC locations of PDO entries, status and diagnostic locations, SDO variables, EDS lint, the adapter type and link settings, simulated devices and the Simulation tool, CAN messages, the gateway, Online access, Connections, the Editor project section, **Copy as ST call**, slave, J1939 and plain CAN networks |
| OpenPLC plugin (removed) | every page is read-only |

Hints and labels follow the target too: a bridge project is not told about OpenPLC or PLC locations, and a CODESYS project not about the Linux device or the bridge, where they do not apply.

A setting the target does not use that the config still has (edited by hand, or from an older config) stays hidden as well, and is not a problem: saving leaves it out of the file, and the save message ends with **(N settings … does not use left out)**. Opening such a file does not mark it unsaved; the next save cleans it. A node tab left with nothing for the target says so in one line instead of staying blank. A CODESYS node has no Emergency (EMCY) section: CODESYS reads the node's emergencies itself.

Switching the target asks nothing: the settings the new target does not use are removed, and a message says how many, with **Undo**. Switching to CODESYS writes each PDO entry's generated variable name into its `name`, so the CODESYS channel keeps the name it had, and removes `bridge` with its connections; switching from CODESYS gives every entry a location again, packed for Modbus (`%IW0` is input bytes 0 and 1, input register 0), with no connections. A version 1 file is saved as version 2. The whole switch is one undo step.

### OpenPLC editor files on save

In a config with an OpenPLC connection inside an editor project, **Save** with no errors in the config also writes `devices/remote/<name>.json`, `pous/programs/canworks_in.st`, `pous/programs/canworks_out.st` and, in `project.json`, the `canworks` variable list and the two programs' task instances (first and last in the task). Save also enables the `canworks` library in the project when it is not enabled (`canworks_in` and `canworks_out` use its functions) and installs it into OpenPLC Editor when it is missing there or older; the save message says when that failed. The user's own POUs are never changed by Save, and a save with errors writes none of these. When one of the three files was changed outside canworks since it last wrote it, Save asks first and names the files: **Write them again** writes them and the config, **Cancel** saves nothing. The save message then says that an OpenPLC Editor with the project open must reopen it before Build. The Project page shows the project and the files Save writes. A config folder outside an editor project writes no editor files; its Project page says so. A config inside an editor project without an OpenPLC connection writes none either: its Project page offers **Use with this OpenPLC project**, which adds the connection as **Add connection** does.

After a canworks update that changes what Save writes (the two programs, the remote device or the `canworks` list), the Project page lists the editor files an older canworks made, **Problems** shows one warning, and **Save** is on although the config did not change. Saving writes those editor files again; `canworks.json` stays as it is. A file you changed in the editor is not listed: Save keeps asking before it writes over it.

A project switched from the removed plugin may still have `main` declare canworks values at the plugin's locations (`rtd_ok : BOOL AT %IX10.0;`), which read nothing now. The Project page then warns, with the first locations, and offers **Use canworks.\* in main**; **Problems** lists the same warning, and the switch's message mentions it. The button (for the saved config) copies `main.st` to `canworks/main-before-move.st`, removes those declarations and the plugin's generated comment, and writes each use in main's code as `canworks.<name>`, leaving comments, strings and names after a `.` alone. Only declarations whose names are members of the `canworks` list move: your own located I/O, other POUs and the config stay as they are, and a name `main` also declares without a location is left and named in the message. The message says how many declarations and uses moved; reopen the project in the editor before Build, where a type that does not fit shows as a Build error on its line.

## Modbus bridge

**Modbus bridge** in the tree appears for a bridge project. The page has:

- **Connections** first (see [below](#connections)).
- **Server**: the listen address and port, the unit ID, the word order of 32- and 64-bit values, the maximum number of clients and of clients per address (default 4).
- **Clients**: who may write, the readers (addresses or prefixes, comma-separated), the watchdog time and what happens to the outputs when the writer is lost (stop, zero, hold or pre-operational, which puts every node of the CANopen master networks pre-operational). With connections, **Who may write** shows the addresses of the connections with **Writes** on. Without connections, **Writers** is a field and required: only the listed clients may write, and empty (the default when the bridge is switched on) means nobody writes. To let every host write, give `0.0.0.0/0, ::/0`. Empty **Readers** means every client may connect.
- **Bridge blocks**: the status and control blocks (the status block is fixed at `%IB4` with the PLC link), a **Live lists** table (one row per CANopen master network, **Add live list**, **Remove**) and the **SDO bridge** request and response blocks with whether clients may write. Each location has **Suggest**, which places the block after the packed data in a free range; a new live list or SDO bridge gets a suggested place at once.
- **Function blocks**: the [mailboxes](modbus-bridge.md#function-block-mailboxes) the library's long SDO, EMCY, CAN frame and J1939 blocks need: a switch (off by default, also after adding an OpenPLC connection), the number of request mailboxes (0-4), the receive mailbox and its receive blocks (1 or 2), the number of cyclic jobs (0-16), network info, and the input and output areas with **Suggest**. Turning it on places both areas in free ranges; with an OpenPLC connection a count change moves them at once. On or off, the section says what works without mailboxes, which blocks need which part with what to use in the config instead, and what the mailboxes cost as a difference: their input and holding registers and, with an OpenPLC connection, the Modbus requests per poll with and without them (budget 40) and about how many CAN frames per second the receiving blocks get at its poll (otherwise: frames per batch, one batch per two of the client's polls). **Who needs them** lists the mailbox blocks the OpenPLC program declares and the connections whose **canworks blocks** choice asks for them. With an OpenPLC connection a note says that the editor project needs Update declarations (Save does it in a project opened here) and a new Build. In an OpenPLC project, Problems shows an error when the program declares a mailbox block whose part is off, with **Turn on what the program uses** (only the parts its blocks need, placed, one undo step), and a warning when the config has mailboxes that nothing needs, with **Turn off the mailboxes** ([plc-library.md](plc-library.md#with-or-without-the-mailboxes)).
- **Register map**: the map of the draft, saved or not, as the bridge serves it: one row per value with its Modbus table, address, size, type, name, source and location, a filter, the input and output sizes, and the suggested client channels (the fewest requests that cover the used registers). **Pack for Modbus** repacks every location densely: data from byte 0, then the status locations, then the bridge blocks. The map files are the Downloads of the connections. When locations break the byte rules the page shows no map, nothing is downloaded, and **Problems** says which locations clash.

### Connections

**Connections** lists the programs and tools that use the bridge's registers (`bridge.connections`, [modbus-bridge.md](modbus-bridge.md#connections)): one row each with its name, kind, address, **Writes**, its state and its actions. With none, the list says that programs, HMIs and Node-RED connect here. **Add connection…** lists the five kinds, each with one line on what it gets: **OpenPLC**, **truST**, **Other PLC**, **Node-RED** and **HMI, SCADA or script**. Every change is one undo step.

- **Download** gives the connection's file, the same as the command line writes: an HMI's register map as CSV, JSON or ST (`<config>-<connection>.csv`), a Node-RED connection's flow (`.json`, [node-red.md](node-red.md), read-only without **Writes** or with the PLC link); the message after it names the Node-RED package the flow needs, and the row's **Package** downloads it (`node-red-canworks-<version>.tgz`, the file `canworks-deploy --export-nodered-package` writes, to install once in Node-RED with Manage palette > Install > upload), a truST or Other PLC connection's `--export-plcopen` folder as a zip ([plcopen.md](plcopen.md)) or, for an Other PLC with format ST, the PLC link file ([plc-library.md](plc-library.md#on-another-modbus-plc)). It stores the map hash in the connection; Save keeps it. The row then reads **In sync**, before the first download **Not downloaded yet**, and after a change that moves the map **Out of date** with **Download again**, also as one warning in **Problems**. A truST or Other PLC connection whose Download the export would refuse reads **Cannot download**, with the reason on hover and as a warning in **Problems** ([modbus-bridge.md](modbus-bridge.md#connections)).
- **Settings** under the row holds the kind's own fields: the format, the bridge address the PLC or Node-RED uses, the library choice, **canworks blocks** (truST, Other PLC and, without the PLC link, Node-RED: None, SDO and send, SDO, send and receive, or All; truST None or SDO and send only), Node-RED's period, and OpenPLC's poll (`poll_ms`, 10 ms by default), remote device name and first editor location (empty: the first free from `%IW100`/`%QW100`) with the facts of the saved config (the remote device and port, the poll with its Modbus requests per poll and the warning above 40, the writer-loss time, the map hash and the first editor locations). An Other PLC's format offers PLCopen XML and ST only; CODESYS uses the CODESYS target.
- **canworks blocks** turns on the mailbox parts the choice needs (one request mailbox, the receive mailbox, 4 cyclic jobs, network info) and places them, keeping parts already on, in the same undo step, and marks a downloaded file **Out of date**. The row then reads, for example, "canworks blocks: SDO and send (1 request mailbox)". Only one connection may have a choice, and none next to an OpenPLC connection: Problems shows an error naming them ([modbus-bridge.md](modbus-bridge.md#connections)).
- A truST or Other PLC connection on a config without the PLC link says so on its row, with **Turn on the PLC link and repack**, one undo step. One without a bridge address while the bridge listens on every address gets a warning on its row and in **Problems**.
- The writers follow the connections: ticking **Writes**, changing an address or adding or removing a connection sets `writers` to the addresses of the connections that write, in the same undo step. A config whose `writers` differ gets a warning with **Use the connections' addresses**; a connection on the network while the bridge listens on loopback only is an error with **Listen on all addresses**. With the PLC link only the PLC writes: a Node-RED or HMI connection with **Writes** gets a warning.
- **OpenPLC** runs next to the bridge on `127.0.0.1`. Adding it turns on the PLC link and low word first, listens on `127.0.0.1:1502` unless another connection is on the network, sets the watchdog, turns on the control block and SDO registers (not the mailboxes: they come on when the program declares a mailbox block), adds a live list per CANopen master network and repacks, all one undo step. In a config folder the dialog also offers **New editor project…** and **Move into project…**, which add the connection on the way. Its row shows the editor files' state (**In sync**, or **Out of date** with **Save**). **Remove** asks first; the editor files stay on disk, and the next Save writes none.

In an editor project, a bridge config is not checked against the project's addresses: the bridge does not run in OpenPLC.

**Install on device…** under the target opens the [Devices workspace](devices.md), which installs the bridge on a Linux device over SSH and starts it with this project's saved config.

## Add a node

**+ Add node…** in the tree (or **Add node…** on an empty network's Bus page) opens the **Add node** dialog:

- **Device description**: the [EDS list](#choosing-an-eds): the project's EDS files (the product name and file name, and how many nodes use it), the files of the [EDS library](#commission-a-canopen-device) when one is set, and **Browse…** for a new file.
- **Node ID**: the lowest free ID, checked as you type (1 to 127, not taken, not the master's).
- **Name**: from the EDS's product name, made a valid identifier and unique in the network; typing your own keeps it.
- **Map the EDS's default PDOs** (ticked): every PDO the EDS turns on by default (COB-ID valid) gets its default mapping, without dummy entries, each entry with a free PLC location; in a CODESYS project each entry gets a variable name instead. On a network without SYNC, a mapped PDO whose EDS transmission type needs SYNC gets type 255 (event-driven), unless the EDS fixes the type, and the message after adding names those PDOs.

**Add** adds the node and opens it on **PDOs**, or on **General** with the name field focused when nothing was mapped. A message shows only when the EDS has findings (corrections made in a copy, accepted lint findings); a clean EDS shows nothing.

A file picked with **Browse…** is imported first. It must be a CiA 306 EDS (objects 0x1000 and 0x1018). It is stored in the config folder as UTF-8, converted from CP1252/Latin-1 when needed, because the editor sends project files as UTF-8 text. If a different EDS with the same name is already there, you choose between replacing it and keeping both. The import also runs the checks the bridge runs before `dcfgen`, under the current EDS lint setting: the message lists the corrections made in a copy (a value written `0x200+$NODEID` read as `$NODEID+0x200`, a REAL value rewritten, an OCTET_STRING value Lely cannot read cleared, with its old text), and shows accepted lint findings as a collapsed list grouped by object. The correction list names the file, says the file itself is kept as imported, gives each kind of correction with how many values it changed, and says who reads the copy for the project's target: the bridge, or for CODESYS the DCFs exported to it, which are built from the copy (a REAL rewrite is not listed there, since the DCFs write REAL values as decimals). A file the bridge could not read, or with a finding that would stop it, is refused with the reason and no node is added. **Check** and saving rerun the lint for every node with its real node ID. The tree follows the name as you type. On **Supervision** pick the supervision method (EDS default, heartbeat or node guarding; only that method's fields are shown; a node with neither, whose EDS has no heartbeat default, is an error shown under the supervision fields, and in **Problems** with the quick fixes **Use heartbeat 1000 ms** (or **Use guarding** when the EDS offers only that) and **Accept no supervision**, each one undo step. A node added from such an EDS gets a 1000 ms heartbeat when its 0x1017 is writable, else node guarding at 1000 ms with life time factor 3, and **Supervision** says it was set when the node was added. A new node also gets **Skip download when unchanged** (`config_check`) when its EDS has a writable 0x1020 sub 1 and 2, and a node that gets its first output entry (an RPDO entry, or a PDO link to it) gets **Watches the master heartbeat** on, with a 100 ms master heartbeat when the master sends none, in the same undo step, when its EDS has a writable 0x1016; once you change that setting it is not set again. A node with outputs that would keep them when the bridge crashes is a warning in **Problems** with **Watch the master heartbeat**, and a SocketCAN adapter the bridge sets up without a bus-off restart is a warning with **Restart after bus-off (100 ms)**; new adapters get 100 ms. A loaded file is not changed by any of this ([What the nodes do](modbus-bridge.md#what-the-nodes-do))) the status bit, the state byte and the boot error byte, and under **Emergency (EMCY)** the EMCY code word, the error register byte and the **EMCY COB-ID** the master listens on: **Device** (the default, saved as no field: read from the node's 0x1014 after each boot), **EDS** (the EDS default, no read) or **COB-ID**, typed in hex or decimal (`emcy_cob_id`, [config.md](config.md#emergency-messages)); the checks report a restricted CAN-ID or one the network already uses with the bridge's message. When the node's EDS has no 0x1014 the device sends no EMCY: the section is one line that says so, with no fields, and a config that still has EMCY fields for it shows them as a problem with **Remove the EMCY settings**. **Suggest** picks a free `%IX` bit, `%IB` byte or `%IW` word. The status bit, state byte, NMT command and boot error byte are grouped as **PLC signals**, whose **Suggest all** fills every empty one.

### Choosing an EDS

Every place that picks an EDS uses the same list, in the **Add node** dialog or in a dialog of its own:

- **Matches this device**: the EDS files whose identity matches a device on the bus, best first, "exact revision" where the revision matches too (in Commission);
- **Built here**: the EDS files generated for a slave of this config (on the slave page);
- **In this project**: the config's EDS files, with how many nodes use each (the files picked on the page, in Commission a device);
- **EDS library**: the library's files, when one is set.

Each entry shows the product name and the file name. The current EDS (or the best match) is selected when the list opens. **Enter** or a double-click on an entry uses it. **Browse…** opens the page's file browser (the folder dialog, listing the EDS files of each folder) in the folder last browsed, else the EDS library; a file picked there is imported and, in a dialog without other fields, used at once.

A page that shows a chosen EDS shows it as text, the product name and the file name, with **Choose EDS…** (none yet) or **Change EDS…**: the node's **General** tab, the [slave device](#slave-networks), the **EDS** column of the Commission Nodes table, and an extra device in the [simulation view](#simulation-view). In Commission, the standard object dictionary, the Parameters tab and the trace's **Decoding** panel and frame inspector open the node's EDS dialog too.

**Notes come with the EDS.** An EDS taken from a folder (**Browse…** or the EDS library) brings the [notes file](#device-notes) next to it, `<EDS file name>.notes.json`, as unsaved edits when the config has no notes for that EDS yet (Save writes them). When the config already has notes for it, they are kept, and the message says the other file can be brought in with **Import notes…**. A `<EDS file name>.datasheet.notes.json` next to it is not taken by itself: the message points to **Import notes…**, which shows its changes first. In Commission a device, which has no Save, the notes file is copied at once next to the EDS picked on the page, unless one is there.

## Advanced settings

The master and each node have a collapsed **Advanced** section with the options `dcfgen` offers. It opens by itself when one of its fields is set, and its title counts them.

- **Master**: start-up (whether the master and the nodes go operational; with **Master goes operational** off the master stays pre-operational and no PDOs move, since the bridge has no command that starts it; start all nodes with one command, reset or stop all nodes when a mandatory node is lost, boot time), heartbeat consumer and timeout factor, the master's own identity, SYNC window and counter, TIME COB-ID and TIME period, EMCY and NMT inhibit times, and error behavior.
- **Node**: mandatory, boot and configure, reset communication, guarding retries, the expected revision and serial number, node ID by serial number (LSS), whether the node watches the master's heartbeat (disabled on **EDS default** when the EDS has no writable 0x1016, which also leaves the Supervision tab's heartbeat watch list with no node to pick), its TIME COB-ID, restore configuration and error behavior.

**TIME period (ms)** (`master.time_period_ms`, 100-3600000) makes the master send the device's time of day (CiA 301 TIME) at that period and at once when the bus comes up; the field shows the COB-ID it goes out on (0x100, or the master's TIME COB-ID). Empty saves nothing and sends no TIME. Nodes that should use it need their TIME COB-ID with bit 31 (0x80000000) set; without such a node the check shows a warning. Keep the device's clock right (NTP), because TIME carries it as it is.

Node-side fields (heartbeat consumer, TIME COB-ID, restore, error behavior) left empty write nothing, so the node keeps its EDS value, which the field shows as its placeholder. Error behavior is typed as `sub=value` pairs, for example `1=0, 3=2`. See [config.md](config.md#node-options) for what each setting does.

**Node ID by serial number (LSS)**: for devices without DIP switches. **Assign node ID by serial number (LSS)** (`lss.assign`) makes the master find the device by the vendor ID and product code of its EDS and the node's **Serial number**, and give it the node's ID at every start, before the network boots; the serial number is then required, and **Reset communication before boot** stays on (the new ID becomes active only on a communication reset). **Store node ID in the device** (`lss.store`) also saves the ID in the device's memory, only when the master had to change it; it is off by default and needs the first box. Unticked boxes are left out of the file. For a node whose EDS does not say `LSS_Supported=1`, both boxes are disabled, with the reason next to them in grey, like every reason an EDS gives for a disabled setting (amber only while the config still has the setting): such a device does not support LSS, and the bridge rejects an `lss` object on it. A loaded node that still has one shows it as a problem, with **Remove the LSS settings** next to the boxes. A device added after **Set node ID** gets no LSS assignment when its EDS has no LSS (the page says so). See [config.md](config.md#lss).

## Map PDO entries

**Add entry…** under a PDO opens the object picker for that PDO: it lists only the objects the node's EDS marks as PDO-mappable, filtered as you type, and **Add** puts the chosen object into that PDO (**Any PDO** lets the page choose: the last PDO of the direction while it has room, 8 entries and 64 bits, otherwise the next PDO the EDS defines). Objects the slave sends are inputs (TPDOs, `%I`), and objects it receives are outputs (RPDOs, `%Q`). The picker at the end of each direction adds to any PDO. The entry's type comes from the EDS, and its location is the lowest free one of the right size from byte 100 up in the bridge's byte image, skipping the bytes the config already uses. You can type any other location, set a PDO's number, COB-ID (a number, or `auto`; the page shows what `auto` resolves to) and transmission type, and move an entry to another PDO. **Remove PDO** removes a PDO with its entries, and a PDO whose last entry is removed or moved goes too; the PDOs after it keep their numbers.

Under each PDO, **Mapping** says who sets its mapping. When the EDS makes it read-only, it reads **Set by the device** and lists the device's mapping, the objects the config uses in bold; the picker then offers, for a direction whose PDOs are all fixed, only the objects of those mappings, and **Add** puts each in the PDO that carries it. **Map all** adds every object of the mapping that is not mapped yet, with suggested locations. When the master may write the mapping, you choose **Write from this config** (the default) or **Use device mapping**, which saves `"mapping": "device"`: the node keeps its EDS mapping, and an entry outside it is shown as an error. See [Devices with a fixed PDO mapping](config.md#devices-with-a-fixed-pdo-mapping).

Under each PDO, **Timing** shows the communication settings the node's EDS defines for that PDO: for a TPDO the inhibit time (in ms, stored in µs), the event timer and, with a synchronous transmission type, the SYNC start value; for an RPDO the deadline (event timer). A setting the EDS does not define is not shown. One it marks read-only shows the EDS value and cannot be changed, and so does a read-only transmission type. Empty fields show the EDS value and write nothing.

Under each input PDO (TPDO), **Timeout** sets its [receive timeout](config.md#receive-timeout): empty is off, a number is milliseconds, and **Auto** uses two times the PDO's event timer, shown next to the field (`auto (200 ms)`), or says that auto needs an event timer when there is none. With a timeout set, **On timeout** picks whether the PDO's inputs keep their last values or read 0 meanwhile, and **Timeout bit** takes an optional `%IX` address (**Suggest** picks a free one). Emptying the timeout drops both.

### Bit channels

An integer entry has **Bits…** next to its variable name, with how many of its bits are mapped (**Bits… (3)**). It unfolds a table of the entry's bits: the bit number, the bit's name from the [device notes](#device-notes) (the CiA 402 statusword and controlword have built-in ones), a tick that maps the bit to a BOOL variable of its own, the variable's name and, on a bridge target, its discrete input or coil number. A newly mapped bit takes the note's bit name as its name (`ready to switch on` becomes `ready_to_switch_on`); type over it to rename it, or leave it empty for the default `<entry part>_bit<n>`. Renaming or removing a note later does not rename a mapped bit. **Map all bits** maps every bit; **Unmap all** removes them. Each change is one undo step.

The bits have no locations of their own: the bridge serves each bit in its entry's location, so an entry keeps its location, and an output entry's unmapped bits keep what the program writes there. In a CODESYS config CODESYS assigns the bit channels. The OpenPLC variable list, the bus trace, the DBC and HTML exports, the CODESYS export and the Modbus register map all use the bit names. With online access, a node's **Object dictionary** shows the mapped bits of an entry under its value, each with its name and on or off. See [Bit channels](config.md#bit-channels).

## PDO links

**PDO links** under a network in the tree (CANopen master networks) lists the network's [links](config.md#pdo-links): a node's TPDO received directly by RPDOs of other nodes. **Add link** starts one from the first TPDO no link uses; pick the producer node and one of its configured TPDOs, and the page shows the COB-ID it takes from the producer (set it on the producer) and the producer's layout, one cell per position sized by its bits. **When the bridge stops** is **Follow the master** or **Keep running**.

**Add consumer…** offers the nodes with a free RPDO. A new consumer gets the first RPDO of its EDS that is not in its `rx_pdos` or another link and, for each producer position, the first object of that size it can receive (or a dummy entry of that size, when its EDS allows one); pick another object per position in the table, or **dummy (skip)** for a value the consumer does not need. A consumer whose EDS fixes the RPDO mapping keeps its device mapping, which must match the producer. Under the table the consumer's layout is drawn below the producer's; a position whose size differs from the producer's is marked, the Problems pane names the link, the consumer and both sizes, and Save stays disabled. **watch producer** adds the producer to the consumer's heartbeat watch, ticked by default when the producer has a heartbeat. **Remove link** asks first.

On the producer's **PDOs** tab its TPDO says which link it feeds (a button to the links page), and its entries may leave the PLC location empty: the consumers get the value anyway. Removing that TPDO asks whether to remove the link too, Cancel being the default.

A node's **Supervision** tab has its **Heartbeat watch** list: each entry names a watched node of the network and a timeout, which shows `default (300 ms)` (the watched node's heartbeat timeout) when empty; **Watch a node…** adds one. The checks are the bridge's, the room in the node's EDS 0x1016 included. A node whose EDS has no writable 0x1016 and that watches nobody has no watch list.

With online access the Online view lists the links of the configuration the runtime runs, with the NMT state of the producer and each consumer, a link marked when one of them is not OPERATIONAL, and the producer TPDO's receive timeout state; the links page shows the states of the Online view's last status next to each node.

## Startup SDO writes

Each node has an ordered list of SDO writes that the bridge performs every time the node is configured at boot, after the PDO parameters. The section is folded while it is empty and shows its count in its heading; **Add…** unfolds it. Pick an object from the node's writable EDS objects, or type its index and subindex.

By default the list shows only settings. It hides process signals (PDO-mappable objects, which belong in a PDO), the communication objects the bridge writes itself from the node's settings (0x1005-0x1007, 0x100C, 0x100D, 0x1014-0x1017, 0x1400-0x1BFF, 0x1F80), and objects already in the list. A line under the list says how many it hid and why. **Show all writable objects** lists everything. A write to an object the bridge also sets is accepted with a warning, because it runs last and overrides that setting. Objects the EDS does not define, or marks read-only or const, are refused, because the bridge would refuse them too. Values are checked against the type's range. An object written twice is marked on both rows: the node keeps the last value. Use ↑ and ↓ to change the order. An object with a [device note](#device-notes) shows its text under the name, with its unit, scale and named values or bits on a second line (also in the picker, and for a note with no text), and the meaning of the value next to it; when the note names values, a list picks a value by name (**Other value…** keeps a typed one). **Note** opens the note editor.

## SDO variables

**SDO variables** lists the objects the program reads or writes over SDO while the network runs (see [SDO variables](config.md#sdo-variables)); like the startup writes, the section is folded while empty. Choose **Read** or **Write** above the picker: it lists the EDS objects that allow that direction (a write never lists `ro` or `const` objects), or type an index and subindex. Objects the EDS does not define are refused. **Add** takes the type from the EDS and suggests a free value location of the right area and size. Each variable is a block: the object, the name, the type, the direction and the remove button on the first line; the value location, the period (read entries), the trigger bit, the status byte, the abort code and the timeout below it, each location with a **Suggest** button. A write to an object canworks configures itself (marked "set by the bridge" in the picker) is accepted with the bridge's warning. The picker rows and the blocks show each object's [device note](#device-notes), and the filters of all three object pickers also match note texts.

The node's **NMT command** field, next to the state byte, takes an output byte (`%QB`) for [NMT commands from the program](config.md#nmt-commands-from-the-program); its hint lists the codes.

## Device notes

A device note explains an object: a one-line text, longer details, a unit, a scale, what each value means, bit names and a manual reference. EDS files have no place for these, so canworks keeps them in a **notes file** next to each EDS in the `canworks/` folder, `<EDS file name>.notes.json` (for example `valve.eds.notes.json`, format `canworks-notes.v1`, JSON Schema in `schema/canworks-notes.v1.schema.json`). Notes are documentation on the PC only: they are never deployed to the PLC, the bridge never reads them, and they never change a value written to a device.

canworks has **built-in notes** for the objects of CiA 301 (communication: heartbeat, PDO parameters, error register, store and restore, ...) and, chosen from the low 16 bits of the EDS's 0x1000 default, CiA 401 (generic I/O) and CiA 402 (drives: controlword and statusword bits, operation modes, option codes, homing methods). A notes file only needs what the device adds or does differently; its fields replace the built-in note's field by field. A sub-object without its own entry uses its object's text, details, unit, scale and manual reference, but not its value meanings or bit names.

The first save creates the notes file of each EDS that has none: the EDS's identity and an entry with the name of each manufacturer-specific object (0x2000-0x5FFF), ready to fill in from the device's manual. A notes file is never replaced afterwards: saving applies only the notes changed on the page and keeps entries and fields written by hand (also unknown fields, such as `x-source`). A notes file that cannot be read is left untouched; **Problems** shows it as a warning and its notes are not used. Importing an EDS under a new name (**Keep both**) gives it its own notes file; replacing an EDS keeps its notes.

```json
{
  "format": "canworks-notes.v1",
  "eds": {"file": "valve.eds", "vendor_id": "0x000000AB", "product_code": "0x00000010", "revision": "0x00010000"},
  "objects": {
    "0x2010": {"name": "Ramp time", "text": "Opening ramp", "unit": "ms"},
    "0x2011:2": {"name": "Fault reaction", "values": {"0": "hold", "1": "close"}},
    "0x2100": {"text": "Valve status", "bits": {"0": "open", "1": "fault"}},
    "0x2200": {"text": "Pressure of the channel", "unit": "bar", "scale": 0.01, "manual": "manual p. 12"}
  }
}
```

Keys are `0x<index>` for a whole object (or a plain variable) and `0x<index>:<subindex>` for one sub-object. `text` is one line of up to 200 characters; `scale` turns the raw value into the shown one (shown = raw × scale); `values` maps raw values to meanings, `bits` bit numbers to names. `name` is informational only. A field set to `null` hides that field of the built-in note: `"0x6098": {"values": null}` drops the built-in homing methods of a drive without homing, and `null` on an object key also stops its sub-objects from inheriting the field (a sub-object with its own value still shows it). `notes check` and **Problems** warn about a `null` that hides nothing.

Where notes show:

- the object dictionary browser: the text under each object, the value's meaning (`3 (profile velocity)`) or the scaled value with its unit (`1234 (12.34 bar)`), bit names in the bit view, and a list to pick a value by name when editing; the search finds note texts;
- the startup SDO list, the SDO variables, the PDO, Startup SDO writes and SDO variables pickers (text, then unit, scale and named values or bits; a long value list stops after six, the rest on hover), and the parameter compare and restore lists;
- the HTML documentation and the DBC export (units, scales, value names, note texts).

Notes are written on the node's **Notes** tab. It opens on **My notes**, the objects you wrote a note for (unsaved edits included; the name-only entries of the first save do not count); **All notes** adds canworks' built-in notes, and **All objects** lists every object of the EDS. Each row says where its note comes from: **Mine**, **Built-in** or **Built-in, changed**. The tab label shows how many notes you wrote ("Notes 4").

- **Note** on a row, a click on the row, or **Add note…** for any object, opens the note editor. **Add note…** lists every object of the EDS with a search by index or name: click a row to pick it, or use ↓ from the search, ↑ and ↓ between rows and Enter (Enter in the search picks the first match). A click that selects text in a row does not open the editor, so note text can be copied. It starts from the built-in note and keeps only what differs from it. Emptying a field that shows a built-in or inherited value hides it (saved as `null`); the empty field then names the hidden value, and **Use built-in** brings it back.
- **Import notes…** reads a notes file (also one made by Export) and shows first what it would do: new notes, changed notes, notes already the same, and entries skipped because the EDS has no such object; a file made for another device or revision gets a warning. Fields that equal the built-in note are not imported, so a merged export brings no built-in text into your file. The import is one draft edit: **Ctrl+Z** takes it back.
- **Export notes…** downloads **My notes** (`<EDS file name>.notes.json`, only your filled entries) or **Merged with built-in** (`<EDS file name>.merged.notes.json`), to share or to start another device's notes from.

Note edits are draft edits like any other: undoable, marked as unsaved, and written to the notes file on **Save**. In Commission a CANopen device, which has no Save, the Notes tab works the same but a kept note or an import is written at once to the notes file next to the node's EDS: in the EDS library for a library EDS, so later projects use the same notes, or in the commissioning folder for an EDS added from a file. A message names the file and offers **Undo**; **Ctrl+Z** also puts back the last note write, and each write is a line in the commissioning log. **Add to a config…** takes the notes written while commissioning along as unsaved edits of the config's notes for that EDS, unless the config already has notes of its own for it (then they are kept and the message says so). Notes of a slave network's own EDS, or in a folder that cannot be written, are shown and exported read-only, and the tab says why. Check names problems in a notes file as warnings that never block saving: a key the EDS does not have, value meanings on a non-integer object, bit numbers past the object's size.

### Notes from a datasheet

Claude can write a notes file from the device's datasheet or manual. The repository has a Claude skill for it, `.claude/skills/canworks-datasheet-notes/`: in Claude Code, opened in a canworks checkout, ask for notes for an EDS and give it the datasheet (PDF, also scanned, DOCX, ODT, HTML or a web page, XLSX or CSV object lists, or text). To use it elsewhere, copy that folder into `~/.claude/skills/`. It needs the PC tools, because it uses the three `canworks-deploy notes` commands ([deploy.md](deploy.md#device-notes)).

The skill writes only what the datasheet states, with the page or section in **manual** on every note (the printed page, and the PDF page when it differs), and leaves out what the built-in notes already say. Where it adds to a built-in list of bits or values it writes the whole list, since a device note's field replaces the built-in one. Where the datasheet and the EDS differ (an object or sub-index only in one, another name, type, size, access, range, default or PDO mapping), it shows all differences in one table before writing, one row per difference or group of the same kind, each answered **Follow EDS** to start with. Accept the table, or change rows: **Use datasheet** (the datasheet's description, with the difference in the details) or **Skip** (no note). Following the EDS keeps its layout, type and range and states nothing the EDS contradicts. Notes cannot change the EDS, so the report names the objects where the EDS may need fixing, and other EDS problems it saw on objects without a note. An EDS that the tools cannot read stops the skill with the line or section to fix. It writes `<EDS file name>.notes.json` next to the EDS only when there is none; otherwise it writes `<EDS file name>.datasheet.notes.json`, which you bring in with **Import notes…** to see the changes first (check the changed rows: they can be notes you wrote).

## Checks and saving

Every change is checked as you type, with the same checks the deploy tool and the bridge run: the JSON Schema, the EDS type and access checks, node ID uniqueness, overlapping locations and SDO value ranges. Errors appear next to their field and in **Problems**, named by node, PDO, object or SDO variable; clicking one goes to its field. **Save** reads **Saved** and is disabled while the draft equals the file on disk (also after a field is typed back to its saved value), **Saved, 2 problems** when the saved config has problems, and **Save** while there is something to save. Save always saves, errors or not: after a save with errors a bar says how many there are and that the bridge refuses the config until they are fixed. The steps that hand the config over refuse it while it has errors, with one line next to their button and **Open Problems**: **Build into CODESYS project…**, **Download for CODESYS**, and installing or starting the bridge on a device (a network without nodes counts here too). The editor's deploy hook runs the same checks. Exports of DCF, DBC and documentation keep their own rules, and **Save to simulation file** still refuses a simulation file with errors; while a save runs it reads **Saving…** and a second click does nothing. On Windows, when another program (often antivirus or a sync client such as OneDrive) holds a file open, a save tries again for about 5 seconds; after that the message names the file and says to try again. A save keeps the key order of the file on disk, so a change of one field is a change of one line. Exports, **Move into project…**, **New editor project…** and **Add node from EDS…** show their progress the same way.

In a project, a CANopen location that a Modbus device, an EtherCAT channel or the pin mapping also uses is an error that names the other file. **Allow overlap** appears in **Problems** under such errors; tick it to count them as warnings, so they stop no hand-off step, as with the deploy tool's `--allow-clash`. It is not saved and is off again when the config is reopened. A located variable at exactly a CANopen entry's location is not a clash: the entry shows that it is declared under that name. A located variable named like a C library macro (`X_OK`, `EOF`, `NULL` and a few more, in any case) is an error: the runtime declares variables in C++ under their upper-case names and cannot compile it. Generated names (**New editor project…**, `--new-project`) skip those names, so a node named `x` gets `x_ok_2`.

Saving writes only `canworks.json`, the imported EDS files and their notes files, in the config folder. Fields the configurator does not know are kept. EDS files no longer used are listed and left in place. If `canworks.json` changed on disk after the page loaded it, saving asks whether to reload it or overwrite it.

Messages about what you did (saved, sent, copied, removed) show in a bar under the header and close by themselves after a few seconds; errors stay until you close them (✕). Switching to another view clears the bar. **Close** and **Reload from disk** ask before discarding unsaved changes, an unsaved simulation or a trace recording that was neither saved nor downloaded, and so does closing the browser tab.

In a window 1100 px wide or narrower the tree folds into a button above the page that names the open entry and the config's error count; it opens the tree over the page, and picking an entry, or Escape, closes it. **Problems** stays in the bottom panel with its count.

**Light / Dark / Auto** under **Settings** in the header picks the page's colours; **Auto** (the default) follows the operating system. The choice is kept in `ui.json` in the configurator's settings folder (the same folder as `online.json`, see [Online access](#online-access)), so it survives restarts; it is never written to the project.

## Export DCF files

**Export DCF** at the top of a node's page, or **This node's DCF** in the Export menu, downloads `node_<id>.dcf`, that node as a CiA 306 Device Configuration File; **All DCFs** in the Export menu downloads every node's file in `<folder>_dcf.zip`. Both export the config as the page shows it, saved or not, and write nothing into the project.

With several networks, **Export DCF** on a node exports that node of the open tab, and **Export all DCFs** asks: **Network `<name>`** downloads the open tab's nodes in `<folder>_<network>_dcf.zip`, **All networks** every network in `<folder>_dcf.zip` with a folder per network (`io/node_2.dcf`, `drives/node_2.dcf`). Each DCF has its own network's bit rate.

Each file is the node's EDS with a `ParameterValue` on every object the master writes to it at boot, a `[DeviceComissioning]` section (node ID, name, bit rate) and updated `[FileInfo]`, checked with Lely's CiA 306 lint before it is offered. If the config has an error or a DCF fails a check, nothing is downloaded and **Problems** names the node, the DCF section and the key. What goes into the file and which checks run: [deploy.md](deploy.md#export-the-nodes-as-dcf-files) (`canworks-deploy --export-dcf` writes the same files).

## Export a DBC file

**DBC** in the Export menu downloads `<folder>.dbc`, the network as a DBC file for CAN bus tools such as SavvyCAN, Wireshark or `python -m cantools monitor`: every configured PDO, each node's heartbeat and EMCY, NMT and, when the master produces SYNC, SYNC. The list next to it picks the SDO frames: **No SDO frames** (the default), **SDO: configured objects** (the config's SDO variables and startup SDOs) or **SDO: all EDS objects**; the choice is kept in `ui.json` with the theme. It exports the config as the page shows it, saved or not, and writes nothing into the project. In an editor project, a signal whose address has exactly one located variable is named after it; otherwise signals carry the object's name from the EDS. If the config has an error, nothing is downloaded and **Problems** says why; warnings (a startup SDO rewriting a PDO's settings) appear there after the download. With several networks it exports the open tab's network, with only that network's nodes, NMT and SYNC, as `<folder>_<network>.dbc`. On a J1939 network it exports the network's received and sent PGNs with 29-bit identifiers ([j1939.md](j1939.md#the-dbc-file)). What goes into the file: [deploy.md](deploy.md#export-the-network-as-a-dbc-file) (`canworks-deploy --export-dbc` writes the same file).

To watch the bus on a PC with a CAN adapter, open the file in SavvyCAN or Wireshark, or run `python -m cantools monitor -c can0 bus.dbc` (cantools 39 or newer; `pip install cantools`).

## Export documentation

**Documentation** in the Export menu downloads `<folder>.html`, one self-contained HTML document of every network for the people who commission and maintain the machine: topology, settings, the COB-ID map with a bus load estimate, each node's identity, PDO layouts, boot SDO writes and object dictionary extract, for a J1939 network the ECU, its messages and signals and the frame map, and a PLC I/O cross-reference. It exports the config as the page shows it, saved or not, and writes nothing into the project. In an editor project, PLC addresses show their located variables, and the project's task interval is the PLC cycle for a network whose SYNC follows it. If the config has an error, nothing is downloaded and **Problems** says why; warnings (an unbounded event-driven PDO, a high worst-case bus load) appear there after the download. What the document holds: [network-docs.md](network-docs.md) (`canworks-deploy --export-html` writes the same document, with options for the title, the object dictionary extract and embedding the EDS files).

A name typed without an extension gets `.project`. While the project file does not exist yet, **PLC device for a new project** is a list of the PLC devices installed in CODESYS on this PC (read from CODESYS's device repository, by name and version), with **Other…** to type `TYPE:ID:VERSION`; for an existing project the page says the bus is added to it. **Build into CODESYS project…** on a project that does not exist and has no PLC device asks to create it, with the same list; **Create and build** saves the choice and builds. Each CANopen master network's Bus page has a **CODESYS** section with the **Network number** and the **CAN interface object**. The PDO tables have a **Variable** column instead of the PLC location: the entry's channel name, with the generated name as placeholder.

**Build into CODESYS project…** (header and CODESYS page) builds the saved config into the project file with CODESYS on this PC, headless, and shows CODESYS's report; unsaved changes are saved first when you agree. A project open in the CODESYS window cannot be built, and the report says to close it there. On a PC without CODESYS, Build says so and offers **Download for CODESYS**, which downloads `<folder>_codesys.zip`: every CANopen master network's node DCFs, the plan `canworks-codesys.json` and the script `import_canworks.py`. Unzip it, open your project in CODESYS and run the script with **Tools > Scripting > Execute Script File...**. Download exports the config as the page shows it, saved or not, and writes nothing into the project; if the config has an error or a DCF fails a check, nothing is downloaded and **Problems** says why. Commission in a CODESYS project connects through a USB adapter on this PC, since no canworks bridge runs the bus. When the build would remove nodes canworks built earlier and that are no longer in the config, it lists them and asks **Remove N nodes** or **Keep them**. **Import from CODESYS…** (start page, and the CODESYS page of a CODESYS config) makes a config from a CODESYS project or a PLCopenXML export, or adds its networks to this one ([codesys.md](codesys.md#import-from-codesys)). Network numbers, re-runs and what carries over: [codesys.md](codesys.md).

## Online access

**Online access** on the Project page (once for the whole config) turns on the bridge's diagnostics channel (the top-level `diagnostics`; see [config.md](config.md#online-diagnostics) and [diagnostics.md](diagnostics.md)). Turning it on generates a random access token, writes only its verifier (`token_verifier`, which does not let anyone log in) into the config, and keeps the token itself in the configurator's settings on this PC (`online.json` in the settings folder: `~/Library/Application Support/canworks` on a Mac, `%APPDATA%\canworks` on Windows, `~/.config/canworks` on Linux), per project folder. It is never written to the project. The page also sets the port, the bind address and **Allow changes** (off by default; turning it on warns that anyone with the token can then write parameters and stop nodes), and the **Runtime host** (`plc.local`, or `HOST:PORT`), which is kept with the token. **Local runtime** next to it sets the host to `local`: the [local runtime](local-runtime.md) on this PC, at the diagnostics port it publishes. When the runtime forces simulation (the local runtime does), the online view says that every network runs simulated.

- **Copy token** copies it, for `canworks-diag` or another PC.
- **Enter token…** takes a token from another PC; it is accepted only if it matches the config's verifier.
- **New token** replaces it; the old one works until the new config is installed on the device.
- **Upgrade** appears for a config from before the encrypted channel (`token_sha256`, which the bridge no longer accepts) when this PC has its token: it writes a `token_verifier` for the same token, so copies of the token on other PCs keep working. Without the token on this PC, use **Enter token…** or **New token**.

Install the config on the device (**Install on device…** or `canworks-deploy --bridge`): the bridge opens the port when it starts with it.

Under the host, a line says whether the runtime host is in the [Devices workspace](devices.md) and what it needs, with **Open in Devices**, or **Install canworks on it…** for a host that is not there yet. The connect panel has **Install canworks on a device…** under the host field, and the status bar lists a running install job with **Show**.

With several networks there is still one Online access for the whole config, one port and one token for all networks, set on the Project page.

On a PC without the host or token yet (a fresh install, another PC), Commission opens on the Nodes table, which says it needs a connection: press **Connect…** in the connection bar, pick or type the runtime and press **Connect**. Up to three recent connections sit at the top of the panel, each connecting in one click; they keep no token. **Runtime** is one combobox: its list has the runtimes found on the local network (by name, filling their address), the ones this PC remembers (by name) and **Local runtime** (`local`), and any host can be typed; the line under it says "Looking for runtimes…" while it searches, then what it found (**Refresh** looks again). A remembered runtime connects directly when it answers and over the [remote link](remote-access.md) otherwise. When this PC has no token for the config, or one that does not match, an **Access token** field (with **Show**) sits in the panel above **Connect**; the token is checked against the config's verifier on Connect and then kept on this PC. There is no second token dialog. The panel says what is missing instead of doing nothing. **Allow changes** is the runtime's setting: the connection bar shows it, read-only, and it changes only with this section and an upload.

**Reachable from other networks** turns on internet access for the remote link (`remote_link.internet`), with an optional list of your own relay servers under it; it takes effect when the program is uploaded. The first connection with the token on the local network pairs this PC with the runtime. **Show paired PCs** lists the PCs paired with the runtime, each with **Remove**, which also ends that PC's open sessions. The online view shows the path (`LAN`, `internet direct`, `internet relayed`) and the round trip next to the connection line, amber above 100 ms and red above 300 ms; on such a path LSS fast scan and a PDO test with a SYNC period ask before they start.

**CiA 309-3 gateway** (under Online access) turns on the CiA 309-3 ASCII gateway (`cia309`, [cia309-gateway.md](cia309-gateway.md)) with **Allow changes** off. It sets the plain port (empty: 7533; 0: none), the sessions at a time, **Allow changes** (SDO downloads, NMT and LSS) and **Allow force on running nodes** (both off by default; force asks first and warns that a standard tool can then stop nodes the program drives), and shows the network numbers (`1 = io, 2 = drives`), with an optional explicit number per network when there are several. The plain port listens on the PLC's loopback address only; other machines connect through `canworks-diag gateway` with the project's token. Check reports the bridge's `cia309` rules, for example `cia309.bind` set to a network address.

## Commission a CANopen device

**Commission a device without a config** on the start page opens **Commission a CANopen device**, which works straight through a CAN adapter plugged into this PC, with no runtime and no config ([pc-adapter.md](pc-adapter.md)). It opens in the Commission workspace with the tabs **Nodes**, **Trace** and **Frame lab**, on the Nodes table, which points to **Connect…** in the connection bar. A config's own Commission workspace works through the runtime, or an adapter on another machine; it has no USB adapter choice.

The connect panel (the bar's **Connect…**) holds the adapter, with up to three recent connections above it ("gs_usb:0 at 500 kbit/s"): one click fills the form in and connects, still with the bit rate check and with **Allow changes** off. Choose a found adapter (**Refresh** looks again) or type one (`gs_usb:0`, `slcan:COM5`, `slcan:/dev/tty.usbmodem14101`, `socketcan:can0`), pick the bus's bit rate, and press **Connect**. There is no default rate and no detection: Connect checks the picked rate first ([the check on connect](pc-adapter.md#the-check-on-connect)) and refuses a wrong one with the reason, keeping the panel open with the form filled in and closing the adapter, so you can pick another rate and connect again. **Node ID for the check** is only for an adapter that cannot confirm its own frames (slcan) on a silent bus: that node must answer an SDO read of 0x1000. Once connected the connection bar shows the adapter and rate, how the rate was confirmed, the adapter's state, the frames and error frames received, another master when one is active on the bus (NMT, SYNC, TIME or SDO requests the PC did not send), the **Allow changes** switch and **Disconnect**. **Disconnect** closes the adapter, with the trace, the transmit list's cyclic jobs, scan and PDO test jobs on it, so other tools can use it. When the adapter goes bus-off or error passive, a burst of error frames arrives, or the adapter stops sending, the connection ends and the bar says why. The adapter, bit rate and check node are kept on this PC (in `online.json`), never in a project.

**Adapter on another machine** in the connect panel (in Commission a CANopen device next to **USB adapter**, with a config next to **Runtime** and **CANopen simulator**) connects to an adapter server (`canworks-diag adapter-serve`, see [pc-adapter.md](pc-adapter.md#an-adapter-on-another-machine)): pick one of the servers found on the local network from the host combobox's list (**Refresh** looks again) or type `HOST[:PORT]` (port 7536 when not given), enter the token the server printed when this PC has none for that server, and press **Connect**. The Devices workspace's **Remote CAN adapter** › **Connect from this PC** opens the panel this way with the device and its token already there ([devices.md](devices.md#remote-can-adapter)). The panel shows the server's adapter and bit rate once known; the bit rate is the server's, so there is no bit rate field, and with a config a server whose bit rate differs from the network's is warned about before Connect and on the Nodes page. The server runs the bit rate check; a refusal keeps the panel open with the reason, and a wrong token asks for the token again. The connection bar then shows the adapter and the server (`socketcan:can0 on benchbox`) with the round trip, and the rest is as with a USB adapter: **Allow changes** (the server must allow changes too), **Disconnect**, which frees the adapter on the server, and the recent connection (`adapter server benchbox`, never with its token). The token is kept on this PC per server, in `online.json`, for every project; **Forget token** removes it. With a config whose online access is off, this target still works.

The lock in the connection bar shows "🔒 Read-only" for every new connection: SDO writes, NMT, restore and LSS are refused until you press **Unlock…** and confirm **Allow changes**. The bar then shows "🔓 Changes allowed" with **Lock**, which goes back to read-only without asking. Either button changes the open connection without closing it. Storing to a device's non-volatile memory still asks each time.

**Nodes** lists every device of this session in one table: heard on the bus (state from its heartbeat, when it was last heard, its last EMCY), found by **Scan the bus**, given a node ID by LSS here, or added with **Add node from EDS…** (the EDS list and a node ID, on this page only). **Scan the bus** reads the identity (0x1018), device type (0x1000) and name (0x1008) of every node ID 1-127, shows its progress, and **Cancel** stops it at once; a send error or an ended connection stops it too and says why. A scanned device is matched against the EDS files in the **EDS library** folder (searched with its subfolders), and its **EDS** column has **Choose EDS…**, whose [EDS list](#choosing-an-eds) starts with the matches. **Choose folder…** next to it opens a folder dialog: **↑** for the parent folder (on Windows, above a drive root, the PC's drives), a path field that takes a typed or pasted path (Enter or **Go** opens it), and the subfolders, each with how many EDS files it holds. A click selects a folder, a double-click or Enter opens it. **Use this folder** sets the library, which is kept on this PC; the row then says how many EDS files it holds with its subfolders (a very large folder, such as the home folder, is only counted in part and the row says scans may be slow). **Clear** removes it. A device does not need a scan to be named: as soon as a node is heard, the page reads its identity in the background (0x1018, 0x1000, the name 0x1008 and the hardware and software versions 0x1009 and 0x100A, a few SDO reads, one node at a time, again after the node boots up, and once a STOPPED node leaves that state). The **Device** column shows the device's name, else the product name of a matching EDS, else its profile from 0x1000 ("CiA 401 I/O device"), else its vendor and product numbers, with the rest in grey; it says **Reading…** meanwhile, and **No SDO answer** with **Read again** for a device that does not answer. The node's heading and its **Status** tab show the same, and **Add to a config…** names the new node after it. Once a node has an EDS on this page, its EDS column shows the file name with **Change EDS…**: the EDS list with the matches first, and **Clear EDS** (back to the standard objects; a node only added from an EDS and not heard offers **Remove node** instead). Each change goes into the log. **Unconfigured devices (LSS)** finds a device without a node ID and sets its node ID or bit rate. Without a connection the table says so and **Scan the bus** is not shown yet. Click a node for its tabs: **Status**, **Object dictionary**, **Parameters**, **PDO test**, **Notes** (written at once, see [Device notes](#device-notes)) and **Log** work as in the [online view](#online-view) (a node without an EDS gets the [standard object dictionary](#standard-object-dictionary)), and **Add to a config…** opens a project or standalone config folder (typed, or picked with **Browse…** in the same folder dialog, which also sets the folder kind when it is an editor project or holds `canworks.json`) with the device added as an unsaved node (a config that already has the node ID, or an EDS that cannot be read, is refused before anything opens): its node ID, its EDS (the one it has on this page, added to the config as an unsaved EDS import; a node without one gets it in its EDS dialog first), its serial number, and LSS assignment ticked when its node ID was set by LSS here.

Every change made through these pages goes into the session log, and so do the bus events seen in this session (state changes, boot results, EMCY, TPDO timeouts, the connection ending). The bottom panel's **Log** shows it (its title counts the entries) with **All**, **Changes** and **Events** filters, and each node's **Log** tab shows that node's entries. **Save log** writes the commissioning record (`node12-commissioning-<time>.txt`: UTC time, node, what and the result, with the device's identity and EDS at the top, no host names or tokens): the changes only, and the bus events too when **Include bus events** is ticked. The log belongs to one commissioning session: **Close** and **Add to a config…** ask to save it when it has unsaved changes, and the next session starts with an empty log. The list keeps the last 5,000 events; changes are never dropped.

**Trace** records through the adapter connection, and its **Send** panel sends on it with **Allow changes**; without a connection it says to connect in the connection bar. Once connected, the page reads the PDO settings of each node it hears (reads only, no **Allow changes** needed): one node at a time, once per connection and again after the node boots up, never from a STOPPED node, and not while another master is on the bus, because two SDO clients on one node can mix their transfers. **Read PDOs from device** under **Decoding** reads a node on demand, and asks first while another master is active. Its message names the PDOs that now decode and, for each other one, the object that could not be read and why (an SDO abort with its text, or no answer after a second try); it is an error when no PDO decodes.

## Online view

The Commission workspace's **Nodes** page (the online view) shows the runtime through the connection and refreshes about twice a second: the bus state and error counters, the master's state, and per node its NMT state, status bit, boot result (with the CiA 302 error letter and Lely's text, and whether a retry is pending), hold (STOPPED or PRE-OPERATIONAL, by the program or by an operator), last EMCY with its CiA 301 class (and the EMCY COB-ID in use with its source when it is not 0x80 + node ID, in red when the device reports its EMCY not valid), SDO variable values, an input PDO that is timed out (`TPDO 1 timed out (2)`, with the number of timeouts so far), and when the node was last heard (any heartbeat, boot-up, EMCY, TPDO or SDO answer; `0.1 s ago`, `-` only when it was never heard). An EMCY 0x0000 (error reset or no error) shows as **cleared (0x0000)** in plain text. A node's Status tab lists its input PDOs with a receive timeout: the timeout, whether it is timed out now (not monitored while the node is not OPERATIONAL), the count and the time since the last PDO. The table updates in place, so keyboard focus stays on a node's row. A connection problem is shown with its reason (host unreachable, port closed, wrong token), here and in the connection bar, and retried. A request that only reads is sent again once after a timeout or a lost connection; a change (SDO write, NMT, LSS, a frame) never is: the view says there was no answer and the change may have been carried out; the node table and the open node's panel turn grey and the view says how long ago the last data came, so stale values are not read as live. **Change…** in the connection bar brings the connect panel back, to change the runtime host. When the runtime runs another config than the saved `canworks.json` (saved but not uploaded yet), the view says so and names the deploy command.

Not connected, the table's place says to connect with **Connect…** in the connection bar. Click a row, or press Enter on its node ID, for the node's page. A network entry on the tree shows this page; a node entry shows only the node's page, which starts with a one-line header (**← Nodes**, the node, its state, when it was last heard, its boot result and the simulated mark, kept live) above its tabs, at the top of the work area. **← Nodes** goes back to the table with the node's row selected. Commission a CANopen device lays out its Nodes table and node pages the same way. Nodes of this page's changes that the runtime does not run yet (added here, not uploaded) are listed too, saying so.

### Scan compared with the config

**Scan the bus** runs through the runtime and compares what answers with the config. When a node is OPERATIONAL the page asks first, naming the nodes the PLC program runs, with **Cancel** as the default: the scan sends SDO requests to every node ID. Progress and **Cancel** are in the status bar. The scan only reads, so it does not need **Allow changes**. Each row then says how the device compares, in words, never by colour alone:

- **Match**: configured, answered, and vendor and product match the node's EDS (revision and serial number too, where the config sets them).
- **Missing**: configured, did not answer and was not heard.
- **Not in config**: answered (or got its node ID by LSS here), no configured node has that ID.
- **Identity differs**: configured and answered, but the identity is not what the config expects; the row names each differing field ("Serial number 0x00000007 on the bus, 0x00000008 in the config").

Before the first scan of a connection the rows say **Heard** or **Not heard**. A summary over the table reads "12 match · 1 missing · 2 not in config · 1 differs", each part a filter (**Show all** clears it). From a row:

- **Add to config** (Not in config, or several ticked rows with **Add N to config**): adds an unsaved node with that ID, the matching EDS (a list when several match, a file picker when none does), the product name, the serial number and LSS assignment when its ID was set by LSS here and the EDS supports LSS.
- **Use matching EDS** (Identity differs, when an EDS in the project or the library matches the device): the node uses that EDS.
- **Take serial number** (only the serial number differs): the node's `serial_number` becomes the device's.

All three are draft edits: the unsaved mark shows, **Undo** reverts them, **Save** saves, and you stay in Commission. A problem that follows (for example no heartbeat for the new node) opens the bottom panel's **Problems**; clicking it leads to the field in Configure.

### State on the tree, Log and Unlock

While connected, each configured node on the network tree shows its NMT state with the [state icons](#colours-and-icons), with its name for screen readers: Operational, Pre-operational, Stopped, the error icon for not answering or boot failed, the hollow circle for not heard. The diagnosis flag marks a new EMCY or error history entry and turns grey when the node sends EMCY 0x0000 (error reset); an EMCY 0x0000 alone raises no flag. A warning or error icon after it marks Identity differs or Missing. The Nodes table and a node's header show the same icons next to the state's name. A change of state is announced. In Configure the tree shows the state only while the connection bar is up.

In Commission with a config the bottom panel has **Log** (open by default) next to **Problems**. The log records the bus events of this session and every change made through Commission, with the same filters as in Commission a CANopen device; **Save log** downloads `<config>-commission-<time>.txt`. It lives in this page only, is never written to the project, and Configure has none.

A control turned off because changes are not allowed says "Locked. Changes are not allowed on this connection." with **Unlock…**. On a USB adapter it asks the same question as **Unlock…** in the connection bar and, once you confirm, turns **Allow changes** on for the open connection; the control is enabled where it is and keeps the focus. On a runtime it says where Allow changes is set (Configure → Online access, then an upload). Controls off for another reason keep their own reason.

### Simulated devices in Commission

Connected to the [local runtime](local-runtime.md) (or any runtime with simulated nodes), Commission works as on a real bus: scan, LSS, object dictionary and Parameters. Simulated nodes are tagged **simulated** in the table, and the simulation file's extra devices show as **Not in config** after a scan or an LSS find, so adding a found device can be practised without hardware. A simulated node's Status tab adds a **Simulated device** panel: its NMT and power state, fault buttons (heartbeat stop, power off and on, resets) with the active faults and **Clear**, and its PDO values with **Override** and **Release**. **Allow changes** governs the panel as in the Simulation view.

When the runtime runs several networks, the connection bar has a **Network** picker that starts on the open tab's network and lists the runtime's networks with their interfaces. Each view shows and acts on the picked network only: its bus state and nodes, and every SDO, NMT, LSS, object dictionary and parameter action goes to that network's nodes. A config with one network stands for the picked runtime network even when their names differ (a runtime that also runs other networks, a config without network names). Picking a network opens its tab, and a trace records that network's interface and decodes with its nodes (an opened trace file is decoded with the picked network's nodes too).

On a slave network the view shows the bridge's own device instead of a master and nodes: its node ID (or that it waits for one from LSS), NMT state, communication OK, SYNC count, last EMCY code with its class and the error register, and the TPDOs and RPDOs in force (COB-ID, off when its invalid bit is set, transmission type and mapped objects, each named with the PLC location and name the config binds it to, the gateway route, or else the dictionary's name, as for the gateway's status objects). On a simulated network the bus says so. On a gateway's upper network a row adds the gateway: the number of routes, whether the upper master is there (missing while its heartbeat is lost) and how many forwarded errors are active. Below it the device opens with the tabs **Status** with the SDO panel on its own dictionary (writing a bound object asks first, as the program, the master's PDOs or the gateway overwrite it) and **Object dictionary** on the slave's EDS, bound objects marked with their location or route and mapped objects with their PDO (the **In a PDO** filter), and **Notes**. The node list, NMT, LSS, the **Parameters** tab and the **ST** copies need a master network and are left out or turned off there; the view says so.

Click a node for:

- **NMT**: Start, Stop, Pre-operational, Reset node, Reset communication; stop, pre-operational and the resets ask first. When the node is OPERATIONAL, the question says the node is running and the PLC program drives it, and the command goes with `force` only after you confirm ([diagnostics.md](diagnostics.md)). An SDO write here or in the object dictionary view asks the same; START never does. Stop and pre-operational hold the node until you start it, the program changes its NMT command byte or sends a `CO_NMT` command. **Copy as ST call** next to the buttons copies, for the command picked in the list next to it, a `CO_NMT` declaration and call for the node with the command's code and name ([plc-library.md](plc-library.md)); it sends nothing, so it works without **Allow changes**. With several networks the call sets `NETWORK` to the online network's number and the instance name carries the network's name.
- **SDO**: pick any object of the node's EDS (or type index and subindex), **Read** it, and see the value decoded with its type (numbers in decimal and hex, VISIBLE_STRING as text, the rest as hex bytes) or the abort code with its CiA 301 text. **Write** encodes a value with the type after a range check, and asks first when the bridge configures that object itself at boot, a startup SDO writes it, an SDO variable of the program writes it, or one of the node's RPDOs carries it (the program writes it every cycle): those win again at the next boot, write or PDO.
- **Emergency history**: the node's last 16 EMCY messages, newest first, with time, code, class, error register and manufacturer bytes.
- **Error history (0x1003)**: the device's own error history, read with the manual SDO read ([diagnostics.md](diagnostics.md)): the count and a row per entry, newest first, with sub-index, code, class and manufacturer information; "no error history (0x1003)" for a device without it; an abort on an entry ends the table with the abort. **Refresh** reads it again. **Clear** writes 0 to sub-index 0: it is turned off, saying why, when changes are not allowed; otherwise it asks first, naming the node and the number of entries (Cancel is the default), asks again when the node is OPERATIONAL and sends the write with `force` only after that, and reads the history again. Works on a runtime and on a USB adapter.

Each node has the tabs **Status** (the parts above; called Overview before), **Object dictionary**, **Parameters**, **Notes** (the node's notes, as on the Configure node's Notes tab: edited in the draft with a config, written at once in Commission a CANopen device) and **Log** (this node's entries of the session log, with their count on the tab), and in Commission a CANopen device **PDO test**. A node opens on Status; the tab picked is kept when you open another node, so you can step through nodes on the Object dictionary. A new EMCY or error history entry flags the node on the tree until its Status tab is opened.

**Object dictionary** shows the node's EDS as a tree, grouped as communication (0x1000-0x1FFF), manufacturer (0x2000-0x5FFF) and device profile (0x6000-0x9FFF). Groups and objects start folded, and after **Read all** the groups that got values unfold, with the objects whose entries differ from the EDS default: a plain object is one row, an ARRAY or RECORD object is a row with ▸ that unfolds its sub-entries, each shown by its own name. Each row has the type, access and EDS default; long names wrap, so the buttons stay in view. Clicking a row, or tabbing to one of its buttons, selects it: the whole row is highlighted with a bar on its left edge, so it is clear which entry its Read, Edit, ST, Note and Watch act on, and the row under the mouse is tinted. The selection stays through reads, the watch list, searches and other tabs; Escape clears it. The tab takes the room of the Problems pane, as the trace does.

<a id="standard-object-dictionary"></a>A node without an EDS (not in the config, none matched or picked) gets the **standard object dictionary**: the CiA 301 communication objects every CANopen device builds on, and the CiA 401 or CiA 402 objects when its 0x1000 names that profile, read, watched and edited as from an EDS, and listed in the SDO panel's object picker too. A line at the top says so and offers **Choose EDS…** (the matching EDS files first) for the device's own objects. The standard has no defaults, so no "≠ default" mark shows. A device may lack some of these objects: a read it refuses as "object does not exist" marks the entry **Not on this device**, and **Hide objects the device lacks** (on by default) hides them. An ARRAY or RECORD shows as many sub-entries as its sub-index 0 says once read (an ARRAY sub-indices 0 and 1 before that), and its **Read** reads sub-index 0 first. **Read all** reads sub-index 0 of each object first, skips the rest of an object the device lacks, and looks past RPDO and TPDO 4 for more until the first missing one, adding those found. **Parameters** (back up, compare, restore, store) needs the device's EDS and says so.

- **Search** on index or name unfolds what matches. The filters next to it narrow the tree further: **Changed from default**, **Writable**, **Set by config or SDO variable**, **In a PDO**, **Not readable**, and after a compare **Different in last compare**.
- **Read all** reads every readable entry one at a time, with progress and **Cancel**; it stops by itself when the node does not answer three times in a row. **Read** on an object reads all its sub-entries; on an entry, that entry. An object row counts its entries that differ from the EDS default or could not be read.
- Marks: **≠ default** (the value differs from the EDS default), **set by config** (the configuration writes it at boot), the SDO variable's name, and the PDO that carries the entry with its bits and PLC location, such as **TPDO1 bits 0-15, %IW100**. Values of PDO-mapped entries are still read over SDO.
- Numbers show in decimal; the small **dec/hex/bin** list switches one entry to hex or binary (two's complement for INTEGER types). **Bits** names the set bits of the error register (0x1001), the manufacturer status register (0x1002) and, on a CiA 402 drive (0x1000 says 402), the controlword (0x6040) and statusword (0x6041); 0x6060/0x6061 show the mode's name.
- **Edit** writes a value in place, with the SDO panel's checks and questions, and reads it back. It shows the EDS LowLimit and HighLimit and asks before writing a value outside them (vendor EDS limits are sometimes wrong; the device has the last word). After a write on a configured node, **Keep in configuration** adds a startup SDO with the value written (not the read-back, which a PDO may have overwritten) to the node, and marks the entry **set by config**, or changes the node's startup SDO for that entry, so the node gets it at every boot without storing it on the device; save the configuration and upload to use it. It is not offered for entries an SDO variable writes, objects the bridge sets itself (for example 0x1017 from the heartbeat setting, the PDO objects), entries another setting writes, and non-numeric types.
- **Read or write any entry** reads or writes an index and subindex the EDS does not list; without a type the value shows as hex bytes. Its **Copy as ST call** copies a call of the SDO function block for it. With several networks the call sets `NETWORK` to the online network's number and puts the network's name in the instance name.
- **ST** on an entry copies Structured Text for the PLC program: a declaration and call of the matching SDO function block (`CO_SDO_READ`, `CO_SDO_READ_STRING`, ...) with node, index and subindex filled in, and the conversion for its type. For a read-write entry it asks whether to copy the read or the write. See [plc-library.md](plc-library.md).
- **Copy** puts the shown rows on the clipboard (tab separated); **Save CSV** saves them. Folded rows are included, rows hidden by the search or filters are not.
- The tree shows the values a compare read; after a write from the SDO panel, a restore or **Write configuration** an entry's value is cleared until it is read again, so no stale value is shown.
- After **Compare** on the Parameters tab, the tree marks each compared entry (**= backup**, **≠ backup: value**, and so on) until you press **Clear**, reload the page or compare again.
- Tick **Watch** on up to 32 entries to read them again (until the first one, a hint line under the filters says so and the Watch list card is not shown) every 0.5, 1, 2 or 5 seconds. The watch list is kept on this PC per project and node (in `online.json`, not in the project) and comes back when you open the project again. It shows each value's age, marks a value that just changed, and keeps the minimum and maximum since watching started (**Reset min/max**). It says how long a round of reads takes and when that is longer than the period, and warns when the node has SDO variables the program reads periodically: watch reads go before them on the bus. **Graph** plots the watched numeric entries over the last 10 minutes; click a name in the legend to hide or show its line.

Without **Allow changes** the tab is read-only and says why.

**Parameters**:

- **Back up** reads every readable entry and downloads a DCF (`node5-rtd-20261005-143000.dcf`): the node's EDS with each value as `ParameterValue`, which other CANopen tools open too. The page asks first when the node has not booted, because the master may not have configured it yet.
- **Compare** reads the node and lists the entries against a backup file, the configuration (what the bridge writes at boot; not offered in **Commission a CANopen device**, which has none) or the EDS defaults: differences first, then entries that could not be read. Read-only entries are left out unless ticked.
- **Restore from backup…** takes a backup file, reads the device and shows what it would write: only manufacturer and profile entries (communication objects when ticked) that differ from the backup, never PDO objects, the store/restore commands or what the configuration writes at boot, each left-out entry with its reason. A backup of another product (vendor ID or product code) needs **Restore to a different product anyway**; a different revision is only a warning. **Hold the node in PRE-OPERATIONAL while writing** is for devices that refuse writes while operational (abort 0x08000022); the node is started again afterwards, also after a failure or **Cancel** (on a USB adapter only when it was OPERATIONAL before). Restored values are not stored on the device.
- **Write configuration…** writes a node's configuration to a device that keeps its own (a device no OpenPLC master configures): from a node of the open config (the node itself by default), a node of another config folder, or a DCF file ([diagnostics.md](diagnostics.md#writing-a-configuration-to-a-device)). It reads the device and shows the plan: each write with the source's and the device's value, PDOs grouped as one sequence each (switched off, mapped, switched on), communication writes marked, left-out entries with the reason, and the identity and node ID checks. **Hold the node in PRE-OPERATIONAL while writing** starts ticked; **Restore defaults first** and **Store on device afterwards** start unticked every time. It writes after you confirm, with progress and **Cancel**, and shows the result with the read-back verdict. **Verify** compares the device with the source without writing. A node of the open config is taken as the page has it, unsaved changes included, and the plan and Verify then say so. On a runtime, a node the runtime configures is refused: change the configuration instead.
- **Factory defaults (0x1011)…** writes "load" to 0x1011, offered when the EDS has it, in the **Device memory (changes the device)** section with **Store on device…**; it asks first, with **Reset the node afterwards** ticked, and says whether the device accepted it.
- **Store on device…** writes "save" to 0x1010 (the subindex chosen: all, communication, application or manufacturer parameters), so the device keeps its current values over a power cycle. It is only offered when the EDS has 0x1010, always asks first, and is never part of a restore, because each store wears the device's flash memory.
- **Restore from backup…**, **Write configuration…**, **Factory defaults (0x1011)…** and **Store on device…** on a node that is OPERATIONAL say so in their question (the PLC program drives the node), and the writes and the hold go with `force` once you confirm.

**PDO test** (Commission a CANopen device only; on a runtime the PLC runs the PDOs) loads the node's PDO layout from the open config when the node is in it, otherwise from the device, and **Start PDO test** shows the TPDOs with their live values, counts and periods, and the RPDOs with an input per entry and **Send** (event-driven RPDOs can repeat). **NMT Start the node first** and **NMT Start** start the node; the SYNC list sends SYNC from the PC at a period, off by default. Every control needs **Allow changes**. With another master on the bus it asks before running anyway. Leaving the tab or closing the page stops the test and the SYNC.

Read all, backup, compare, restore, write configuration and verify run in the configurator, not in the page: reloading the page or switching tabs does not stop them, and the tab shows a running one again. One runs at a time.

With **Allow changes** off, the write, NMT, restore and store buttons are disabled and say why; reading, backup and compare still work.

**Unconfigured devices (LSS)** commissions devices without DIP switches (needs **Allow changes**; otherwise the panel is disabled and says why). **Find a device without node ID** searches the bus with LSS fastscan, up to about 15 seconds, and shows the one device it found: vendor ID (with the vendor name from a matching EDS), product code, revision, serial number and a matching EDS from the project or the EDS library. Then:

- **Set node ID…** suggests the lowest node ID that is neither configured nor the master's. A device that had no node ID starts with the new one at once; one that had another keeps it until it is reset or power-cycled. Afterwards the device is on the Nodes table as **Not in config**, with **Add to config**: it adds a node with that ID and EDS, its serial number and **Assign node ID by serial number** ticked when the EDS supports LSS, so the master gives it the ID at every start. Nothing is written to the project until you save. A node ID outside 1-127 keeps the dialog open and says so.
- **Set bit rate…** sets the device's bit rate for its next power cycle; the rest of the bus keeps its rate, so connect again at the new bit rate once every device is set.

Both dialogs have **Store in the device**, unticked every time a dialog opens: without it, a power cycle undoes the change. Find the next device after setting one.

## Trace

**Trace** records the bus through the runtime, or shows a trace file, decoded as CANopen ([trace.md](trace.md)), or as J1939 on a J1939 network ([j1939.md](j1939.md#diagnostics-and-trace)). Opening, viewing and exporting files works without a connection; recording uses the connection in the connection bar (a runtime with [online access](#online-access), or the USB adapter in Commission a device) and opens a runtime connection that is set up; without one the view says to connect in the connection bar. A running recording is listed in the status bar with its frame count. Frames are decoded with the saved `canworks.json`: PDO signals by their names (in an editor project, the PLC variables at their locations), SDO objects by their EDS names. When commissioning a device, the trace decodes with the CANopen predefined identifiers and the EDS files picked on **Nodes**, and decodes PDOs too: with the layout the bus set (SDO writes in the trace, for example another master's boot), else the layout read from the device, else the EDS defaults, marked **assumed** ([trace.md](trace.md#decoding-without-a-config)). DBC files added under **Decoding** decode their identifiers in every workspace.

One toolbar holds every trace action:

- **Start** begins a trace and turns into **Stop**. Without a connection it opens the connect panel, and the trace starts once connected (**Close** leaves Trace as it was); **Clear** empties it. Start and Clear ask first when the recording shown was neither saved nor downloaded, naming the frames that would be lost; Enter keeps the recording. After a recording of the same network, Start offers **Continue this trace**: the new frames follow the old ones after a gap marker. **Capture** holds the capture filters (ID and mask) and **Record error frames**, applied from the next Start. When the bridge is older than this feature, Start says it is too old for traces and to update it.
- **Decoding** ▾ says what the trace decodes with and shows it on the button ("Decoding · 1 DBC, 3 nodes", with ⚠ when a file needs attention). **DBC files** lists the files added with **Add DBC…**: how many of each file's messages are used, the messages not used and what decodes their identifier instead, ↑ and ↓ to change the order (the first file wins on a shared identifier), **Remove**, and **Locate…** for a file that has gone. The files are kept on this PC per project folder, and once for Commission a device, never in the project; a file added from the browser is copied to the `dbc` folder in the configurator's settings folder. **Nodes** lists each CANopen node heard or on the Nodes table with its device name, EDS ("none" without one) and where its PDO layout comes from (configuration, set on the bus, read from the device with the time, EDS defaults, "not read" when the last read gave no usable PDO, or unknown when never read), with a line for each PDO the last read could not make usable and why; in Commission a device each row has **Choose EDS…** (**Change EDS…** once it has one), which opens the node's EDS dialog, and **Read PDOs from device**.
- **Open…** opens a pcapng, candump log or Vector ASC file. **Save** ▾ holds **Save to traces folder**, which writes the trace in the chosen format to the `traces` folder in the configurator's settings folder and shows where, and **Download** (pcapng, candump log, ASC, BLF, TRC, CSV, or the chosen graph series as a signals CSV). Both take the whole trace, the graph's zoom, or the time between cursors A and B.
- The header names where the frames come from (the runtime, the adapter or the file). When the connection ends while recording (the adapter is unplugged or goes bus-off, or the runtime does not answer for 10 seconds), the recording stops with "connection ended" and its reason, and the frames stay.
- **⧉ Open in new window** opens the trace in a window of its own, so it can be watched while this window sends from the online view, the PDO test or SDO reads and writes. The window shows only the Trace view and its transmit list, under a line naming the folder, network and connection, and uses this window's connection (**Connect…** stays here). This window's Trace tab then says the trace is open in its own window, with **Show trace window** and **Bring trace back here**. **Explain in Frame lab** in the trace window opens the Frame lab here. Recording goes on when either window closes, and only the last window showing an unsaved recording asks about it on closing. The window keeps its last size.
- The line under the buttons counts the frames, the duration, the frame rate and estimated bus load while recording, error frames, frames lost on the way or dropped by the PLC's kernel (by the adapter machine's kernel, named, on an adapter on another machine), and how many the display filters show.

The tabs:

- **By identifier** (the first tab) has one row per identifier, format and direction, so Tx and Rx of one identifier are two rows. Each row shows the newest data, its decoded line, the count and the last, average, minimum and maximum cycle time, and when it was last seen. While recording, the table updates in place four times a second, so a row never jumps: the bytes that changed in the last second are tinted and underlined, and bytes that never changed are greyed. **Set reference** marks every byte that differs from the data each identifier had at that moment (for a file, at the selected frame), and the identifiers that are new since; **Clear reference** removes the marks. A row whose identifier stopped (no frame for three average cycles, and at least a second) turns italic and says silent. Column headers sort the table, and the sort is kept. **Pause view** stops the table while the recording goes on, and says how many updates wait; the button then reads **Resume view**. Up and down arrows, Page Up, Page Down, Home and End select a row; its newest frame shows in the inspector (when it is open) and follows the row until **Hold frame**, and a line says which bytes and bits changed since the previous frame. **Show frames** opens the row's identifier in Chronological, **Graph signals** charts its signals.
- The bar under **By identifier** and **Chronological** makes the list taller or shorter, for both lists (drag it, or Up and Down when it has the focus; double-click for the default). The heights are kept on this PC.
- **Chronological** lists the decoded trace, newest at the bottom; **Follow** keeps the newest frames in view while recording, with the newest one whole at the bottom, and scrolling up stops it. Times are relative to the trace start or UTC. Even a trace of 2 million frames scrolls smoothly: the page only fetches the rows in view.
- **Filters** ▾ holds the display filters (nodes, frame kinds, an ID range, direction, and text in the decoded line) of both lists and counts the ones set; they only change what is shown, recording goes on.
- The **frame inspector** starts as its slim **Inspector** rail until a frame is clicked. It sits beside the list on a window 1440 pixels wide or more, and from 1280 to 1439 pixels it opens as a drawer over the right part of the list, so the list keeps its columns. On a narrower one it sits under the list, and the two share the window's height, each scrolling on its own, so the selected row and its explanation show together (on a phone they stack on the page). The divider resizes it. **✕** in its title bar, or Esc inside it, closes it and leaves a slim **Inspector** rail that opens it again; clicking a frame or pressing Enter on it opens it too, while the arrow keys move through the list without opening it. It shows what the frame says, its identifier bits split into function code and node ID, every data bit coloured by its field with the PLC address it lands in, and the frame rebuilt bit by bit on the wire with its stuff bits and time on the bus. Pointing at or tabbing to a bit explains it and lights the same bit in every layer ([frame-inspector.md](frame-inspector.md)). The identifier, data and wire layers fold from their headings, and a folded layer keeps a one-line summary; what you fold stays folded for every frame, in the Frame lab too. **About this kind of message** stays open or closed as you left it, and while the inspector follows new frames of one identifier it keeps the explained bit, its scroll position and focus. **Explain in Frame lab** opens the frame there with the trace's SDO context; **Send…** adds it to the transmit list. For a PDO decoded without a config, a **Layout** line says where its layout came from; for a PDO shown only as bytes it says why and offers **Choose EDS…** and **Read PDOs from device** for its node.
- **Sequences** lists SDO conversations (as sequence diagrams between the PLC and the node), boot stories (each node's boot with the master's writes compared to the configuration's) and SYNC cycles (a timeline per SYNC period with the SYNC window, stepping and a jump to the slowest cycle). Picking a conversation or boot story keeps the list where it is. Every step opens its frame in the inspector.
- **Graph** plots the chosen series: PDO signals, bus frame rate and estimated load, EMCY codes and SDO aborts, and while recording each node's NMT state and status bit, the bus state and error counters, and the SDO variables (read from the runtime twice a second). A network's first graph starts with its first PDO signal ticked, and a series name cut in the list shows whole on hover or focus. Series in the same lane share a chart; lanes share the time axis and the cursor. Scroll the mouse wheel over a chart to zoom in or out at the pointer (Ctrl+wheel and a trackpad pinch too), Shift+scroll or a sideways swipe to pan; drag to zoom to a range, double-click or **Whole trace** to zoom out, ◀ ▶ to pan. Zooming in stops at a 100 µs window. The bar under the charts makes every lane taller or shorter (drag it, or Up and Down when it has the focus; double-click for the default). A click sets cursor A, Shift+click cursor B; the table under the charts shows each series at A and B and the difference. **Show A in frames** selects the frame at cursor A in the list, **Back to graph** returns; a selected frame's **Show in graph** puts cursor A at it. Trigger hits and lost frames are marked in every chart.
- **Trigger** sets one condition, or two joined by AND or THEN, its count, single or normal mode, the pre- and post-trigger times, and auto-save of each hit's window ([trace.md](trace.md#triggers)). It applies to the next Start, and at once to a running recording. Hits are listed with buttons to show each in the frames or the graph.

The trace is kept by the configurator, not the page: reloading the page or switching views keeps it, and a recording goes on until Stop. The recording uses one of the bridge's 4 diagnostics client slots. The tab, the divider positions, whether the inspector is shown, its folded layers and the sort are kept on this PC.

### Transmit list

The **Transmit list** under the trace sends CAN frames by hand through the page's connection, the runtime or the adapter ([diagnostics.md](diagnostics.md#sending-frames-by-hand)). Each row has a name, the identifier in hex, **Ext** for a 29-bit identifier, **RTR** with its DLC for a remote frame, up to 8 data bytes, a period and a count. A row without a period is sent once with **Send**; a row with a period (10-60000 ms) is a cyclic job started with **Start**, which runs until **Stop**, until it has sent its count, or until the page closes, and keeps running while you use other views. The row says what it decodes to, whether the identifier is one the network uses, and its state: idle, sent at what time, running with how many frames sent, or refused with the reason. Mistakes are named under the row as you type. **Stop all** stops every job, the header counts the frames and running jobs, and the ⋯ menu explains a row in the Frame lab, duplicates, moves or removes it.

**Send…** on a trace frame, a By identifier row or in the Frame lab adds that frame to the end of the list and sends nothing; you send it from the list. Sending needs **Allow changes**; without it the list says so and can still be edited. When the runtime or the adapter asks for force (the identifier is one the network uses, or a node is OPERATIONAL), the page shows its reason and sends only after you confirm. Sent frames show in a running trace as Tx.

The list is kept on this PC for each project folder and network, so it is there again after a reload or the next day. **Save list…** downloads it as `<network>.transmit.json`, **Open list…** adds a saved list to this one or replaces it (and asks when the file was saved for another network), **Clear list** asks first.

## Frame lab

**Frame lab** explains frames without a runtime, a trace or an adapter, and sends nothing (its **Send…** only adds the frame to the Trace view's transmit list). The frame box at the top takes a typed or pasted frame (`185#2500EA00`, `705#7F`); under it, the tabs **Examples** (frames made from the configuration on the page, saved or not, one row per node), **Build** (an SDO read or write, a PDO from signal values, an NMT command, a heartbeat or an EMCY) and **Arbitration**. The result shows beside them on a window 1280 pixels wide or more, and under the frame box on a narrower one, and comes into view by itself. It opens in the same inspector as in the Trace view, at the network's bit rate or one picked from the list. **Clear**, or Esc in the frame box, removes it and empties the frame box. A frame opened from the trace with **Explain in Frame lab** keeps the trace's SDO context and says which frame it came from, until you change it; **Back to trace** returns to that frame. **Arbitration** sends two frames at the same moment, bit by bit, and shows where one sender reads a dominant bit it did not send and stops ([frame-inspector.md](frame-inspector.md#frame-lab)).

## Simulation view

**Simulation** in Commission shows and moves the [simulated devices](simulator.md) while they run; **Edit the simulation file** switches to **Simulation file** in Configure, which edits `simulation.json`, the file that says what they do from the start, and its scenarios (run from Commission → Simulation). It takes the room of the Problems pane, as the trace does.

The view shows the simulated devices of the connection in the connection bar; it has no connect form of its own:

- **Runtime**: the simulated devices of the runtime. Without online access the view says what to set up.
- **CANopen simulator**: a running `canworks-canopen-sim`, picked in the connect panel (**Connect…**, then **CANopen simulator**) by **Simulator address** (`HOST[:PORT]`, default `127.0.0.1:7532`) and its **Token** when it was started with one. Both are kept on this PC in `online.json`, per project folder, never in the project. The connection bar then shows the simulator's address and **Disconnect**; the Nodes table and trace recording need a runtime and say so.

Without a connection the view says once that live values need one; the simulation file and the scenarios stay editable.

The line under the heading says, once connected, whether the network is simulated or real (with its interface), how many devices are simulated, and whether changes are allowed. A connection problem is shown with its reason and retried; a runtime that simulates nothing says so. Without **Allow changes** on the runtime the view is read-only and says why: values still refresh, but the controls and buttons are disabled. A CANopen simulator takes changes from anyone with its token.

The view has three tabs.

**Live values** lists the simulated devices: node ID (or none, for an extra device waiting for LSS), name, network, NMT state, power, a node ID conflict (a real device with the same node ID on the bus, which powers the simulated one off), active faults, and how many objects have a source or an override. Click a device for its **Values** and **Faults**.

- **Values** has a row for every object in the device's PDOs, every object with a source or an override, and every object you pin (**Pin**, from the EDS list or typed as `0x2000:1`; pins are kept on this PC). Values refresh about twice a second. A number has a slider between the EDS LowLimit and HighLimit, or the type's range when the EDS gives none; a BOOLEAN has a switch, and an UNSIGNED8 or UNSIGNED16 a switch per bit. Moving a slider, a switch or a bit holds the value as an override, marked **override**, until **Release**. **Set** writes the typed value once (a source moves it again), **Override** holds it.
- **Source…** opens the object's value source: constant, sine, triangle, sawtooth, square, ramp, step sequence, random walk, counter, CSV time series or expression, each with its own fields, and noise and tick for all ([value sources](simulator.md#value-sources)). An expression is checked as you type, by the simulator when the view is connected (otherwise by the configurator, when its checker is installed, else not until it is given): an error is shown with its position in the text and a mark under it. **Apply** gives the source to the running device and puts it in the simulation file's draft; **Remove source** takes it away from both.
- **Faults** has a button for every [fault](simulator.md#faults): **EMCY…** (code, error register, manufacturer bytes, repeat period), **Heartbeat stop**, **Power off**, **Power on**, **Power cycle…** (off time), **Reset node**, **Reset communication**, **NMT state…**, **SDO abort…** (object, abort code, on read, write or both, how many times), **SDO delay…**, **Refuse writes while operational**, **TPDO stop…**, **Identity…**, **Device type…**, **Forget node ID**, and on a CiA 402 drive **Drive inputs…** (blocked, limit switches, home switch). Buttons without … act at once; the others open their fields with **Inject**, and **Add to faults at start** puts the fault in the simulation file instead. **Active faults** lists the device's faults, each with **Clear**; **Clear all** clears every fault and powers the device on.

**Simulation file** edits the draft of `simulation.json`, also without a connection: the tick, and per node of the config (and per extra device) **Default behaviour** (off saves `"default_behaviour": false`), its value sources (**Add source…**, **Edit**, **Remove**), its faults at start. A node that is not simulated in this config keeps its entry, which does nothing. **Extra devices** adds devices that are not in the config, to try a scan, LSS commissioning or an identity check: an EDS from the config folder (or its `eds/` subfolder) or **Pick EDS file…**, a node ID (or none, then a name is needed). They are saved to the file and take effect at the next start of the simulation.

**Scenarios** lists the file's scenarios and those the simulator knows, with whether each is in the saved file, its state (running, passed, failed, stopped), the running step, the time since it started, and its result: a failed scenario shows the failed step, the condition and the value seen. **New scenario** creates one; **Edit** opens its steps. Each step has its action (set, override, release, source, fault, clear, wait, expect, log, repeat) with that action's fields, the device it acts on, and when it starts (when the previous step ends, at a time since the start, or a time after the previous step). A wait or an expect takes a condition on an object (device, object, optionally a bit, a comparison and a value) or an expression, checked as you type; a wait has a time-out, an expect holds now, within a time or for a time. A repeat holds its own steps. Problems with a scenario show under its steps as you edit. **Start** runs a scenario (one edited here and not saved yet runs as edited), **Stop** stops a running one, **Delete** removes it from the draft.

**Save to simulation file** writes `canworks/simulation.json` (in a standalone folder, `simulation.json` next to `canworks.json`) after checking it against its schema ([version 1](../schema/canworks-sim.v1.schema.json), or [version 2](../schema/canworks-sim.v2.schema.json) with a section per network), with the save rules of the config: only into the config folder, the EDS files that extra devices use and that were picked here, and a question when the file changed on disk after it was loaded. A file with problems is not saved, and the problems are listed. The line next to the button says whether there are unsaved changes. **Reload from disk** and opening the project read the file again; the next simulated start uses what was saved.

With several networks the view works on the section of the network picked at the top: sources, faults at start, extra devices and scenarios go into that network's section, the other sections are kept as they are, and a note over the editor names the section. A version 1 file opened with a config of several networks is put in the first network's section and saved as version 2; **Save to simulation file** asks before converting it ([simulator.md](simulator.md#version-2-a-section-per-network)).

## From standalone to project

In a standalone config, **Move into project…** in the Project page's **Editor project** section copies the saved config, its EDS files with their device notes and its DBC files, with `simulation.json` and the CSV files it names and a slave EDS's description, into an editor project's `canworks/` folder, after the same checks as `canworks-deploy --into-project`. It asks before replacing an existing `canworks/` folder, which is then kept as `canworks.bak-<time>`. The page then switches to the project, and the address checks run against it.

## A new editor project from a standalone config

Starting without an editor project, **New editor project…** in the Project page's **Editor project** section (standalone mode, configs with an OpenPLC connection) creates one around the saved config. Give the folder to create it in, the project name and the task interval (default `T#20ms`). The configurator runs the editor's own `openplc-cli create` (so the project shows in the editor's recent projects), sets the target to OpenPLC Runtime v4, copies the config in as **Move into project…** does, and writes the [OpenPLC editor files](#openplc-editor-files-on-save): the remote device for the bridge, `canworks_in`, `canworks_out` and the `canworks` variable list. `main` is an empty program for your own code, which uses the values as `canworks.<name>`. If a runtime host is saved in the online settings, it becomes the project's runtime address. **Install the canworks library in the project** (off by default) also enables the `canworks` function block library in the project and installs it into the editor if needed ([plc-library.md](plc-library.md)). The mailbox blocks also need the bridge's mailboxes, which Problems offers once the program declares one ([plc-library.md](plc-library.md#with-or-without-the-mailboxes)). The page then switches to the new project; open it in the editor with **Open Project**.

An existing folder is refused, and the standalone folder is left as it was. This needs the editor's `openplc-cli` on the PATH (the editor installs it on first run, or run `openplc-cli install-cli`) or `$OPENPLC_CLI`; the same is available as `canworks-deploy --new-project` ([deploy.md](deploy.md#a-new-editor-project-from-the-config)).

## Then, in the editor and on the device

1. Write the program in `main` with the `canworks` variables.
2. **Build and upload** as usual: the upload carries the program and the remote device to the runtime.
3. Install the bridge with this config on the device with **Install on device…** (the [Devices](devices.md) workspace), or upload the config to a running bridge with `canworks-deploy --bridge <host>` ([deploy.md](deploy.md)).
