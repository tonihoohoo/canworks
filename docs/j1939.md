# J1939 networks

A network with `"protocol": "j1939"` makes the PLC an ECU on a J1939 bus (SAE J1939 on 29-bit CAN identifiers, as in vehicles and mobile machines). The PLC claims a source address, receives parameter groups (PGNs) from other ECUs into `%I` locations, sends PGNs from `%Q` locations, answers requests and asks other ECUs for PGNs. J1939 and CANopen networks can share one config file (`schema_version` 2), each on its own interface.

The plugin uses the Linux kernel's J1939 stack (`CAN_J1939` sockets): the kernel handles the transport protocol (BAM and RTS/CTS, messages up to 1785 bytes), and the plugin does the address claim, the signals and the PLC image. The PC tools use [can-j1939](https://github.com/juergenH87/python-can-j1939) for the simulator.

[`examples/j1939`](../examples/j1939) holds a complete config and its DBC file: a PLC at address 128 that reads pressures, a temperature and a level from an engine ECU at address 0, asks it for component data (a 40-byte PGN) once a second, and sends a speed setpoint and an operating mode.

## The kernel module

J1939 needs the kernel module `can-j1939`. `scripts/install-stock.sh` loads it and lists it in `/etc/modules-load.d/canworks-j1939.conf`, so it loads at every boot; in Docker installs it does this on the host. Raspberry Pi OS ships the module. On Ubuntu it is in `linux-modules-extra-$(uname -r)`.

Without the module a J1939 network does not start and the log says so ("J1939 needs the can-j1939 kernel module (modprobe can-j1939)"); its state byte reads 3 (no bus). The plugin retries every 5 s, so loading the module later is enough. CANopen networks in the same config run regardless.

A plugin built without J1939 (`install-stock.sh --without-j1939`) refuses a config with a J1939 network: "J1939 is not built into this plugin (built with: canopen)". `--without-canopen` builds J1939 only, without Lely or dcfgen.

## The config

```json
{
  "name": "machine",
  "protocol": "j1939",
  "adapter": { "type": "socketcan", "interface": "can0", "bitrate": 250000 },
  "j1939": {
    "ecu": {
      "name": { "identity_number": 1234, "function": 130, "arbitrary_address_capable": true },
      "address": 128,
      "address_range": [128, 135],
      "state_location": "%IB200",
      "address_location": "%IB201"
    },
    "dbc": "machine.dbc",
    "rx": [ { "pgn": 65280, "name": "Pressures", "source": 0, "timeout_ms": 300, "status_location": "%IX202.0",
              "signals": [ { "name": "Pressure", "start_bit": 0, "length": 16, "scale": 0.1, "unit": "bar",
                             "iec_location": "%IW210", "valid_location": "%IX202.1" } ] } ],
    "tx": [ { "pgn": 65281, "name": "Setpoints", "period_ms": 100,
              "signals": [ { "name": "Setpoint", "start_bit": 0, "length": 16, "iec_location": "%QW210" } ] } ],
    "requests": [ { "pgn": 65282, "destination": 0, "period_ms": 1000 } ]
  }
}
```

J1939 is usually 250 kbit/s (500 kbit/s on newer machines). The adapter settings are the same as for CANopen ([config.md](config.md)).

### The ECU

| Field | Meaning |
|---|---|
| `name` | The 64-bit NAME, by field: `identity_number` (21 bits), `manufacturer_code` (11), `ecu_instance` (3), `function_instance` (5), `function` (8), `vehicle_system` (7), `vehicle_system_instance` (4), `industry_group` (3), `arbitrary_address_capable`. Fields left out are 0. A lower NAME wins an address contention. |
| `address` | The preferred source address, 0..253. |
| `address_range` | `[low, high]`: where the ECU may move when it loses its address to a lower NAME. Needs `arbitrary_address_capable`. |
| `state_location` | Byte input: 0 claiming, 1 claimed, 2 cannot claim, 3 no bus. |
| `address_location` | Byte input: the address held, 254 while none is. |

At start the network asks every ECU for its claim, listens 250 ms, then claims `address` unless an ECU with a lower NAME holds it. The claim stands after another 250 ms; until then nothing else is sent. Against a lower NAME, an arbitrary-address-capable ECU moves to the next free address of its range; otherwise, or with the range used up, it sends Cannot Claim and stays silent (state 2). A contending claim from a higher NAME is answered with our claim, and requests for the address claim are answered. In state 2 the answer is Cannot Claim, sent after a pseudo-random wait of 0 to 153 ms (J1939-81) drawn from a generator seeded with the NAME.

When the interface goes down, the adapter is unplugged or the controller reaches bus-off, the state goes to 3, inputs hold their values, and the network claims its address again when the bus is back.

### Received PGNs (`rx`)

| Field | Meaning |
|---|---|
| `pgn` | 0..0x3FFFF. A PDU1 PGN (PDU format below 0xF0) has its low byte 0; it is taken when sent to our address or to global. |
| `source` / `source_name` | Take the PGN only from this source address, or only from the ECU with this NAME (`source_name_mask`: the NAME bits to compare). Without either, from any ECU. |
| `timeout_ms` | 0: no supervision. Otherwise `status_location` goes FALSE when nothing arrived for this long, and TRUE again with the next message. Values hold their last value meanwhile. |
| `status_location` | Bit input: TRUE while the PGN arrives. |
| `signals` | See below. |

### Sent PGNs (`tx`)

| Field | Meaning |
|---|---|
| `pgn`, `destination` | The PGN, and for a PDU1 PGN the destination address (default 255, global). |
| `priority` | 0..7, default 6. |
| `period_ms` | Send every `period_ms`. 0: send when a value changes (no faster than `min_gap_ms`) and when requested. |
| `min_gap_ms` | With `period_ms` 0: the least time between two sends on change, default 0. A change within the gap goes out when it has passed. |
| `length` | Bytes; default the smallest length of at least 8 that holds every signal. Over 8 bytes the kernel sends with the transport protocol. |

Values come from the last finished PLC scan; nothing is sent before the program's first scan. Unused bits are sent as 1 (J1939 "not available"). A change the interface refuses to send (a full transmit queue) does not count as sent: the PGN goes out with its current values once the interface takes frames again.

### Requests

A Request (PGN 59904) for one of the network's `tx` PGNs, to our address or to global, is answered with the current values; a request to our address for any other PGN gets a NACK. Each `requests` entry asks `destination` (an address, or 255 for every ECU) for its PGN every `period_ms` (100 ms or more); the answer is received like any other PGN when an `rx` entry names it.

Requests for the same PGN from the same ECU are answered at most once every 50 ms; requests in between are ignored. This also holds for NACKs and for requests for the address claim, except those from the null address (254) sent by ECUs that are still claiming.

### Signals

| Field | Meaning |
|---|---|
| `start_bit`, `length` | As in a DBC file: the least significant bit for little byte order, the most significant one for big. 1..64 bits. |
| `byte_order` | `"little"` (default, the J1939 order) or `"big"`. |
| `signed` | Two's complement; the value reaches the PLC sign-extended. |
| `scale`, `offset`, `unit` | For the tools only (declarations, trace, configurator). |
| `iec_location` | `%I` for a received signal, `%Q` for a sent one, wide enough for `length` (X 1 bit, B 8, W 16, D 32, L 64). |
| `valid_location` | Received signals: a bit input that is FALSE while the signal arrives as not available (all ones) or error (all ones minus one), for signals of 2 bits or more. The value location keeps its last value then. On a PGN with `timeout_ms` it also goes FALSE when no message carried the signal for that long (a multiplexed page that stopped). |
| `multiplexer`, `mux` | Multiplexing, as for raw messages; see [Multiplexed PGNs](#multiplexed-pgns). |

### Multiplexed PGNs

A PGN can carry different signals in the same bytes, picked by a switch signal (the DBC's `M`, or `mNM` with `SG_MUL_VAL_` for nested switches). The fields and rules are those of raw messages ([raw-can.md](raw-can.md#multiplexed-messages)): a switch has `"multiplexer": true`, a dependent signal has `"mux": { "on": "Page", "values": [1, [4, 7]] }`, and signals on different pages may share bits.

A received multiplexed PGN, also one that arrives through the transport protocol, updates its switches, its page's signals and the signals of every page; the other signals keep their values. A switch value with no page counts as `unknown_pages` in the diagnostics status. A sent PGN with a switch has `pages`: `program` (default; the switch has an `iec_location` and the program picks the page), `all` (every page each period, the plugin sets the switch) or `rotate` (one page per period). A request for the PGN is answered with every page in `all`, the next page in `rotate` and the program's page in `program`. `all` and `rotate` take at most 64 pages.

Values reach the PLC raw. The program scales them; the declarations the tools write carry the scaling as a comment:

```
VAR
    machine_Pressure AT %IW210 : UINT;  (* x 0.1 + 0 bar *)
END_VAR

pressure_bar := UINT_TO_REAL(machine_Pressure) * 0.1;
```

## The DBC file

`dbc` names the network's DBC file, relative to the config. The plugin does not read it; the configurator imports messages from it, the trace decodes with it and the simulator runs it. In the configurator, **Import DBC** on a J1939 network copies the file into the project's `canworks/` folder and turns the picked messages into `rx` or `tx` entries with free PLC locations ([configurator.md](configurator.md#j1939-networks)). `canworks-deploy --export-dbc` writes a J1939 network's `rx` and `tx` PGNs as a DBC with 29-bit identifiers.

## Simulator

`canworks-j1939-sim` plays one node of a DBC file on a SocketCAN interface or a USB adapter on the PC, for testing a PLC program without the other ECUs:

```sh
canworks-j1939-sim --dbc machine.dbc --node Engine --interface can1 --address 0
canworks-j1939-sim --dbc machine.dbc --node Engine --adapter slcan:COM5 --scenario engine.json --log engine.jsonl
canworks-j1939-sim --contend 128 --name-value 0x10 --interface can1     # take address 128 from the PLC
```

It claims its address, sends the node's messages at their DBC cycle time (`GenMsgCycleTime`) with values ramping between the signals' limits, or as a scenario file sets them, answers requests, and prints every message it receives decoded. A multiplexed message goes out as every page each cycle, or one page per cycle in turn with `--mux rotate`. `--help` describes the scenario format and the NAME options.

## Diagnostics and trace

With diagnostics on, `canworks-diag status --network machine` shows the claim state, address and NAME, the ECUs seen on the bus, each received PGN (sources, age, timeouts, raw signal values) and the counts of sent PGNs, answered requests and sent requests. Operations that only make sense for CANopen (SDO, NMT, LSS, parameters) are refused on a J1939 network.

`canworks-diag trace` and the configurator's **Trace** view decode a J1939 network's frames with its DBC: priority, PGN, source and destination, scaled values with units (for a multiplexed PGN the switch values, such as `Page=2`, and only that page's signals), address claims with their NAME fields, requests, acknowledgements and transport protocol sessions. `canworks-diag explain` and the frame inspector split a 29-bit identifier into its J1939 fields ([frame-inspector.md](frame-inspector.md)).

## Limits

- One J1939 network per interface; J1939 and CANopen cannot share an interface.
- No diagnostic messages (DM1 and others) are generated or decoded as such yet.
- Values are raw integers of up to 64 bits; floating point signals are not supported.
