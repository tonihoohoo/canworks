# CiA 402 drives as PLCopen axes

A CiA 402 servo or stepper drive on the CANopen bus can be driven from the PLC program with the PLCopen motion blocks that come with the OpenPLC Editor (`MC_Power`, `MC_MoveAbsolute`, `MC_MoveVelocity`, `MC_Home`, ...). The config marks the node as an axis, the project generator writes the glue, and the program calls the blocks on an axis named after the node:

```
power(Axis := drive, Enable := TRUE);
move(Axis := drive, Execute := power.Status, Position := 1000.0, Velocity := 500.0);
```

The plugin does nothing different on the bus for an axis: the drive's objects travel in ordinary PDOs, and the axis logic runs in the PLC program. The example in [config/cia402-drive/](../config/cia402-drive/) has a made-up drive, its config and a demo program.

## What you need

- **OpenPLC Editor 4.3.2.** The example builds with its Build only for OpenPLC Runtime v4. Its built-in PLCopen SoftMotion library (`AXIS_REF_SM3`, the `MC_*` blocks and the CiA 402 drive bridge `SM_Drive_GenericDS402`) is part of every project; no EtherCAT device is needed. The library is the editor's (GPL-3.0) and is not in this repository. Other editor versions may change it; the tests here run against the compiler version 4.3.2 uses (STruC++ 0.7.0).
- A drive whose EDS has the CiA 402 objects as PDO-mappable objects, and whose PDO mapping is writable or already holds the objects you need.

## The config

Add `axis` to the node (see [config.md](config.md#cia-402-axis)):

```json
{
  "node_id": 4, "name": "drive", "eds": "servo402.eds",
  "heartbeat_ms": 50, "heartbeat_timeout_ms": 200,
  "status_location": "%IX10.0",
  "axis": { "scale_numerator": 1, "scale_denominator": 1, "scale_factor": 1.0 },
  "rx_pdos": [ ... 0x6040, 0x6060, 0x607A, 0x6081, 0x60FF ... ],
  "tx_pdos": [ ... 0x6041, 0x6061, 0x6064, 0x606C ... ]
}
```

The axis takes the drive's objects from the node's PDO entries, by object (sub-index 0). Each one feeds one pin of the bridge:

| Object | Name | PDO | Type (IEC) | Needed |
|---|---|---|---|---|
| 0x6040 | controlword | RPDO | UNSIGNED16 (UINT) | yes |
| 0x6060 | modes of operation | RPDO | INTEGER8 (SINT) | for more than one mode |
| 0x607A | target position | RPDO | INTEGER32 (DINT) | profile position |
| 0x6081 | profile velocity | RPDO | UNSIGNED32 (UDINT) | profile position |
| 0x60FF | target velocity | RPDO | INTEGER32 (DINT) | profile velocity |
| 0x6071 | target torque | RPDO | INTEGER16 (INT) | no |
| 0x6041 | statusword | TPDO | UNSIGNED16 (UINT) | yes |
| 0x6061 | modes of operation display | TPDO | INTEGER8 (SINT) | for more than one mode |
| 0x6064 | position actual value | TPDO | INTEGER32 (DINT) | for positions |
| 0x606C | velocity actual value | TPDO | INTEGER32 (DINT) | for velocities |
| 0x6077 | torque actual value | TPDO | INTEGER16 (INT) | no |

Objects that are not mapped are left out of the bridge call and stay at the library's defaults. The node also needs its **status bit** (`status_location`): the bridge reads it as "drive online", so a lost drive puts the axis into error stop instead of looking like a drive at standstill.

The deploy tool, the configurator and the project generator refuse an axis node without the status bit, without 0x6040 in an RPDO or 0x6041 in a TPDO (each with a location), with a standard object in the wrong direction, of another type or mapped twice. They warn when the EDS device type (0x1000) is not profile 402, and when a target object is mapped without 0x6060 (the blocks set the mode themselves, so without it the drive stays in the mode it starts in).

**Transmission types** default to the EDS's own values, as for every PDO. With event-driven TPDOs (255, the example) the drive sends the statusword when it changes and the positions on its event timer; with synchronous types the config needs SYNC, best from the PLC cycle (`"sync_source": "plc_cycle"`, see [config.md](config.md#sync-from-the-plc-cycle)) so each scan sees fresh drive values.

**Ramps and homing** are drive parameters: set them with startup SDOs (the example sets profile acceleration 0x6083, deceleration 0x6084 and homing method 0x6098). `MC_Home` runs the drive's homing mode (6) with the method the drive has.

## Scaling

The three `axis` fields are the library's scaling of its position unit to drive increments: `scale_numerator` increments for `scale_denominator` units, times `scale_factor`. With `"scale_numerator": 10`, `MC_MoveVelocity` with velocity 25.0 sends target velocity 250 and the axis reports 25.0 back. Left out: 1, 1 and 1.0, so units are increments.

## The generated program

`openplc-canopen-deploy --new-project` and the configurator's **New editor project…** declare in `main`, after the node's located variables:

```
drive        : AXIS_REF_SM3;          (* node drive (4): CiA 402 axis *)
drive_bridge : SM_Drive_GenericDS402; (* node drive (4): drive bridge of axis drive *)
```

and put the scaling and the bridge call first in the program body:

```
(* CiA 402 axes from canopen/canopen.json: keep these lines first *)
drive.iRatioTechUnitsNum := DINT#1;
drive.dwRatioTechUnitsDenom := DWORD#1;
drive.fScalefactor := LREAL#1.0;
drive_bridge(Axis := drive,
             wStatusWord := drive_Statusword,
             ...
             bOnline := drive_ok,
             wControlWord => drive_Controlword,
             ...);
```

Keep these lines before your own code. For an existing project, the configurator's **Variable declarations** gives the same lines to paste. The generator writes `main` once: after a change to the axis node's mapping, update the bridge call by hand or paste it again.

**Timing.** The bridge runs once per scan: the blocks see this scan's PDO inputs, and their commands go out with the outputs at the end of the scan, so a command reaches the drive one PLC cycle (plus the PDO's own timing) after the block runs. That suits the profile modes, where the drive runs the profile itself.

## Cyclic synchronous modes

In the cyclic synchronous modes the program computes the motion and sends the drive a new set-point every PLC cycle: a position (CSP, mode 8), a velocity (CSV, mode 9) or a torque (CST, mode 10). The drive applies it on SYNC and interpolates between two set-points. This needs a SYNC every PLC cycle and synchronous PDOs, and four blocks of the `openplc_canopen` library drive it. The example is [config/cia402-drive/canopen_config_cyclic.json](../config/cia402-drive/canopen_config_cyclic.json) with the demo program [drive_cyclic_demo.st](../config/cia402-drive/drive_cyclic_demo.st).

### Config

```json
"master": { "node_id": 1, "sync_source": "plc_cycle" },
"nodes": [ { "node_id": 4, "name": "drive", "axis": { "cyclic": true },
  "rx_pdos": [ { "transmission": 1, "entries": [ 0x6040, 0x6060, 0x607A ] },
               { "transmission": 1, "entries": [ 0x60FF, 0x6071 ] } ],
  "tx_pdos": [ { "transmission": 1, "entries": [ 0x6041, 0x6061, 0x6064 ] },
               { "transmission": 1, "entries": [ 0x606C, 0x6077 ] } ], ... } ]
```

`"cyclic": true` on the axis turns on the checks (deploy tool, configurator, plugin):

- errors: the network's SYNC does not come from the PLC cycle (`"sync_source": "plc_cycle"`), or `sync_cycles` is not 1 (with the master's timer, scan and SYNC drift and a set-point is applied twice or skipped; with more cycles per SYNC the drive misses set-points); 0x6060 or every set-point (0x607A, 0x60FF, 0x6071) is missing from the RPDOs; an RPDO with the controlword, the mode or a set-point is not synchronous (transmission type above 240, after the EDS's defaults); `interpolation_period_us` cannot be written to 0x60C2;
- warnings: a TPDO with the actual position or velocity is not synchronous; the EDS has no 0x60C2 or no 0x6065; 0x6502 does not list the mode of a mapped set-point.

The plugin writes the **interpolation time period** 0x60C2 during the node's configuration: `interpolation_period_us`, or the runtime's base tick (the PLC cycle when the program's task runs at the base tick). Sub 1 is 1-255 and sub 2 the exponent of 10 (10 ms is 10 and -3, 2.5 ms is 25 and -4). It leaves 0x60C2 alone when a startup SDO writes it or the EDS has none. After 100 SYNCs it compares the measured mean SYNC interval with that period and warns once per node when they differ by more than 10 %. `openplc-canopen-diag status` shows the period of each cyclic axis.

In the configurator, **Cyclic synchronous** under the node's CiA 402 axis sets `cyclic`; on a network with SYNC from the timer the node shows the error with a **Use SYNC from the PLC cycle** button. **Map CiA 402 objects** on a cyclic axis uses the layout above and sets transmission type 1 on the PDOs it fills, listing each change.

### Blocks

The blocks are in the `openplc_canopen` library (`library/openplc_canopen/`, built into `openplc_canopen.stlib`), which the project generator enables for a config with a cyclic axis. They take the same `Axis : AXIS_REF_SM3` as the `MC_*` blocks and work in the axis's units:

| Block | Mode | Inputs | Similar blocks elsewhere |
|---|---|---|---|
| `CO402_CyclicPosition` | 8 | `Enable`, `Position`, `MaxVelocity` (step limit, 0 = off) | `SMC_FollowPosition` |
| `CO402_CyclicVelocity` | 9 | `Enable`, `Velocity`, `MaxAcceleration` (step limit, 0 = off) | `SMC_FollowVelocity` |
| `CO402_CyclicTorque` | 10 | `Enable`, `Torque` (per mille of rated torque), `MaxTorqueRate` (per mille/s, 0 = off) | `SMC_SetTorque` |
| `CO402_CyclicMoveAbsolute` | 8 | `Execute`, `Position`, `Velocity`, `Acceleration`, `Jerk`, `Window` (0 = one increment) | `MC_MoveAbsolute` in CSP |

Outputs: `InSync` (the drive shows the mode, operation is enabled and the set-points are applied), `Busy`, `Done` (move block, on reaching `Position` within `Window`), `Error` and `ErrorID`: 1 the drive is not enabled, 2 the drive did not show the mode within `ModeTimeout` (default T#500ms) or left it, 3 a set-point step above the limit, 4 the axis is in error stop (drive fault or lost drive), 5 (move block) a limit is not above 0 or the plan failed.

How they start: with the axis powered (`MC_Power.Status`), on a rising `Enable` or `Execute` the block sets the set-point to the actual value (position) or 0 (velocity, torque), writes the mode to 0x6060 and keeps "enable operation" set, so the motor stays under control while the drive changes mode. It follows its input once 0x6061 shows the mode. A set-point step above the limit times `Axis.fCycleTime` stops the block with error 3 and holds the last set-point instead of clamping it, so a wrong trajectory in the program shows. In the scan `Enable` goes FALSE, the velocity and torque blocks send 0, and then the block stops writing: call only the block in use, and call it once with `Enable := FALSE` when its step ends, as the [demo](../config/cia402-drive/drive_cyclic_demo.st) does. `CO402_CyclicMoveAbsolute` plans a jerk-limited move from the actual position with the editor library's S7RTT planner and sends one point of it per cycle. To stop in a cyclic mode, ramp the velocity block to 0 (the demo does): `MC_Halt` and `MC_Stop` set the halt bit, which a drive handles its own way, or not at all, in modes 8 to 10. The `MC_*` profile blocks can take over afterwards; they select their own mode.

### fCycleTime

The blocks take the cycle time from `Axis.fCycleTime`. The generated program sets it for a cyclic axis from the task interval (`--task-interval`, default T#20ms; the configurator's declarations panel has a task interval field for it):

```
drive.fCycleTime := LREAL#0.01; (* the task interval: change it with the interval *)
```

Change the line when you change the task interval.

### Timing

With SYNC from the PLC cycle and synchronous PDOs, the loop is fixed: a set-point written in one scan is applied at the second SYNC after it, and the position the program reads was sampled at the SYNC before the scan. At constant velocity the actual position the program sees is therefore about three cycles times the velocity behind the set-point it just wrote (30 units at 1000 units/s and 10 ms), every cycle the same. The drive measures its following error against the set-points it has applied, so this delay does not count against its window 0x6065; set the window for the drive's own lag (the example sets it with a startup SDO). A following check in the program must allow the three cycles.

When the PLC stops, SYNC stops, and the drive faults on its interpolation watchdog (the simulated drive sends EMCY 0x8700 after three periods). After a restart the program sees the axis in error stop: `MC_Reset`, then start again, as the demo does.

`MC_ReadStatus` reports a cyclic axis as in discrete motion (the library knows no cyclic state); use the blocks' `InSync` instead.

## What works

- **Modes:** profile position (1), profile velocity (3) and homing (6) with the editor's `MC_*` blocks; cyclic synchronous position (8), velocity (9) and torque (10) with the `CO402_Cyclic*` blocks ([above](#cyclic-synchronous-modes)).
- **Blocks:** `MC_Power`, `MC_MoveAbsolute`, `MC_MoveRelative`, `MC_MoveVelocity`, `MC_Home`, `MC_Halt`, `MC_Stop`, `MC_Reset`, `MC_ReadStatus`, `MC_ReadActualPosition`, `MC_ReadActualVelocity`, `MC_ReadAxisError`, as the library provides them: one active move at a time, its own error IDs. The tests here use `MC_Power`, `MC_MoveAbsolute`, `MC_MoveVelocity`, `MC_Home`, `MC_Halt`, `MC_Reset` and `MC_ReadStatus`.
- **Errors:** a drive fault (statusword fault bit) and a lost drive (status bit FALSE) put the axis into error stop; `MC_Reset` sends the fault reset.

## How the library behaves

Four points from the tests against the library, each handled in the [demo program](../config/cia402-drive/drive_demo.st):

- **Execute is level, not edge.** A block acts while `Execute` is TRUE; hold it until `Done`, then set it FALSE.
- **Call a block only while it is in use.** An idle block still writes its controlword bits, so calling every block every scan makes them fight over the controlword. Call each in its own step of a sequence.
- **Select homing mode before `MC_Home`.** Started from another mode, `MC_Home` can act on statusword bits of the previous mode before the drive has switched, and fail. Set `drive.Drive.Modes_of_operation := 6` and wait for `drive.byRealControllerMode = 6` first.
- **`MC_MoveAbsolute.Done` counts only after `Busy`.** It can be TRUE in the first scan, before the drive has taken the new set-point. Wait for `Busy`, then `Done`.

The editor's debugger cannot show the axis state and the blocks' error IDs (the library's enum types are opaque to it; Build only warns about each). Watch them through `MC_ReadStatus` and `MC_ReadAxisError` outputs instead.

A drive takes the fault reset on a rising edge of controlword bit 7, so if the fault is still active when `MC_Reset` runs, run it again later (the demo retries every 50 scans).

## Tests

- `test/cia402/run.sh` compiles the generated `main` of the example with STruC++ 0.7.0 (fetched by `scripts/fetch-strucpp.sh`, needs Node 22) and runs ST tests against an ST model of a CiA 402 drive: power on, absolute move, velocity, fault and reset, lost drive, scaling, and the demo program.
- `sim_tests --exact sim_cia402_demo` runs the compiled demo program as the PLC program through the real master against a simulated CiA 402 drive on the in-process virtual bus. Build with `cmake -DSTRUCPP=$(scripts/fetch-strucpp.sh)`; without it the test only says it was not built.
- The cyclic blocks have ST tests in the same run (`test_cyclic.st`, `test_cyclic_demo.st`: bumpless start, mode refused, step limit, S-curve move, torque, fault and lost drive, and the cyclic demo). `sim_tests --exact sim_cia402_cyclic` runs the cyclic demo with SYNC from the PLC cycle against the plugin's simulated drive: 0x60C2 written, the sequence without a fault or an oversized set-point step, the drive faulting when the PLC stops and the program bringing it back.
- `sim_tests --exact sim_gantry_demo` runs the [gantry cell example](../examples/gantry-cell/README.md): three cyclic axes and a [simulated machine](machine.md) that gives the drives home switches, limit switches, load and jams, so a program's homing, straight-line moves and fault recovery can be tried on a PC.

No real drive has been tested yet.

## Related work

- **SYNC from the PLC cycle** (`sync_source`) is what the cyclic synchronous modes run on.
- **SDO from the program at run time** would let the program set ramps and homing, or read the drive's error code 0x603F, while running; until then they are startup SDOs.
- **Several CAN networks**: axis names are node names, so they must stay unique across networks.
